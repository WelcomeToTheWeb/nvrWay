### Zone ids in the row, zone names on the wire

The event row accumulates zone **ids** (`applySignalTo` unions `in.ZoneID` into
`zones_json`; the worker's `zone_name` is validated and discarded), while an
operator types "porch" into a search box and the console draws zone chips by
name. So `api/events.go` resolves the pair from the camera row in both
directions: `cameraRefs.zoneNames` (id → name, for the view) and
`cameraRefs.zoneIDs` (lower-cased name → ids, for `q`). A zone id the camera row
no longer knows falls back to the id in `zones` — the event did happen in a zone
that has lost its name, and inventing a name would be worse.

`EventFilter` gained `QZoneIDs []string` (the store change): the handler resolves
names, the store still does the matching. Capped at `MaxQZoneIDs = 32` — the cap
bounds the statement, not the answer.

### The `q` clause is parenthesized by hand

`TestEventsListQIsScopedToTheCameraItWasAskedFor` is the reason. GORM joins
separate `Where` calls with `AND`, and unparenthesized SQL reads
`camera = B AND class LIKE q OR zones LIKE q` as
`(camera = B AND class LIKE q) OR zones LIKE OR …` — camera A's zone match would
answer a request that named camera B, a filter that quietly widens itself. The
clause is wrapped in explicit parentheses rather than trusting the builder.

### Name matching runs in Go, not SQL

sqlite's `LIKE` is case-insensitive for ASCII; Postgres' is not. A `q` that
matched "Porch" on the test database and not on the deployment is a bug nobody
can reproduce, so the zone-name half of `q` is resolved in Go with
`strings.Contains` on lower-cased names. The row's own `q` match stays in SQL:
its values (class names, rule names, zone ids) are written by this server in a
known case.

### `truncated` at the ceiling costs one extra query

The segment manifest (S4-05) asks for `limit+1` and skips the probe at the
ceiling. That does not work for events: the store clamps `limit` at 200, so at
`limit=5000` the extra row is clamped away and 200 rows out of 250 would answer
`truncated: false` — a timeline that looks complete exactly where it is cut. A
full page is instead probed with one row at `offset+limit`
(`probe.Limit = 1`), which is one extra query only when the page is full. The
assertion that pins it is in `TestEventsListLimitDefaultsTo50AndClampsAt200`.

### The delete: order, jobs, and the ledger

Cancel the armed assembly (`ClipScheduler.Cancel`, the need S6-01's interface
already named) → queue the remote purge → remove the local files → delete the
row. A row that outlives its files is a named 404; files that outlive their row
are bytes nothing will reclaim, because the sweeper walks rows and never
directories. Remote copies go into the queue rather than being deleted inline:
the tier may be a WebDAV share behind a tunnel, and deleting one event should
neither block on it nor fail because it is down. With no backend configured the
answer says `no storage tier is configured: nothing remote to purge` instead of
failing — a local-only installation is a stated state.

The delete is `admin`, not `operator`, and the two refusals land in the ledger
next to the one success (`TestEventsDeleteIsAdminOnlyAndWritesTheLedger` asserts
1 ok + 2 refused rows for `event.delete`).

### Purge job ids: `<event_id>:clip` and `<event_id>:snapshot`

A job row is keyed by its object, so one event's two media need two ids — the
shape the camera purge (S3-03) already uses, and the shape this card reuses
rather than inventing a second one. **It will not land on Postgres**:
`storage_jobs.id` is `type:uuid` and a suffixed id is not a uuid (proven against
postgres:16-alpine — `ERROR: invalid input syntax for type uuid:
"…:clip"`). sqlite, the test target, stores the column as text and accepts it,
which is why the suite is green. Filed as [`P-08`](P-08.md); it is one bug with
two call sites, and fixing it is a schema decision, not an event-surface one.

### What S6-05 still owns

The clip route serves the local file with `http.ServeContent`, so `Range:
bytes=…` already answers 206 (asserted here, because it is the delivery this
build has). What is left is the copy that exists only on a tier:
`clip_uploaded_at` set with no local file answers the named 404 and logs
`streaming from the backend is S6-05`. That route needs S7-01's `Backend.Get`.
