## Notes

Plan's Verification section: a pin break is a pin bump recorded in the same commit.

- **The plan's stage 1 does not run: `import cv2` needs libxcb.** `pip install
  ultralytics==8.4.195 onnx==1.17.0` then `YOLO(...).export(...)` dies before the export
  even starts:

  ```
  File "/usr/local/lib/python3.12/site-packages/ultralytics/utils/__init__.py", line 26, in <module>
      import cv2
  ImportError: libxcb.so.1: cannot open shared object file: No such file or directory
  ```

  ultralytics imports cv2 at *package* import, and the `opencv-python` wheel it depends on
  is the GUI build, which links X11 — absent from `python:3.12-slim`. Stage 1 now installs
  `libgl1 libglib2.0-0 libxcb1 libx11-6 libxext6 libsm6` (after the pip layer, so a fix
  here does not invalidate the torch download). They live in the discarded stage only: the
  runtime image keeps the plan's `opencv-python-headless` and needs none of them. The other
  fix — swapping `opencv-python` for headless inside stage 1 — was rejected because
  ultralytics' dependency auto-check can pip-install the GUI wheel back mid-export, which
  would make the failure come and go with the network.
- **The exported bytes are not reproducible from the two pins, and the hash is a record
  rather than a check.** The export logged `requirements: Ultralytics requirements
  ['onnxruntime', 'onnxslim>=0.1.82'] not found, attempting AutoUpdate...` — ultralytics
  pip-installed two **unpinned** packages during the export, and `onnxslim 0.1.98` then
  rewrote the graph. The same pins exported by hand on the same day produced
  `63786071b848c00b22f8ffa17104cbd9380e99aa7d83f5e7d6d9ae01e8d03f4e` where the image build
  produced `d23c126273b9083b5f60b1e77a3183713c9415dee43ff4d7e62f7a4f22ff506e` — different
  bytes, identical inference (3 people in `bus.jpg`, best conf 0.890, the same box to the
  micrometre). So `fixtures.json` records the hash and says plainly that a build whose hash
  differs is not broken; a build whose model fails the smoke test is. Making the hash
  enforceable would mean pinning `onnxslim` and `onnxruntime` in stage 1 as well, which is
  a decision for whoever bumps the pair.
- **`ENV NVR_MODEL_PATH` in the skeleton was a name nothing reads.** The worker parses
  `DET_MODEL_PATH` (the plan's name, plan line 170); the skeleton set `NVR_MODEL_PATH`, so
  the image's env was decoration and the worker ran on its own default — the same path, by
  luck. Renamed, and `GO2RTC_URL` is now set explicitly next to it.
- **The compose service mounts `nvr_models:/models` over the baked-in model**, which works
  only because Docker populates an empty *named* volume from the image's content at that
  path on first use. It is what lets an operator swap the model without a rebuild, and it is
  worth knowing it is a copy-on-first-use: a volume created by an older image without a
  model stays empty, and the worker exits 2 saying exactly what is missing.
- **The dependency graph had a cycle, and this card was one end of it.** S5-12 listed
  `depends: S9-02, S10-01` while S9-02 lists `depends: S5-12` — so neither could ever move
  to done — and S10-01's deliverable is the fetcher that *reads* `testdata/fixtures.json`,
  which this card's own criterion says is written here, on the first successful build. The
  edges are now what the cards' own text describes: this card stands on the pins (S5-01) and
  on the Dockerfile skeleton it edits (S0-03). What is left for the others: S9-02 owns the
  server/web images, the compose wiring and the non-root/CMD assertions; S10-01 owns
  `scripts/fetch-fixture.sh` reading `assets[]` from the file written here.
