14 tests, all `--- PASS`, and `go build ./... && go test ./... -count=1` is green
across every package (`api` 4.874s, `auth`, `config`, `models`, `sso`,
`sso/testidp/provider`, `store`, `ws`); `gofmt -l .` prints nothing. The walk is
real: `authorize -> the IdP's /authorize -> our /callback -> the fragment`, driven
against the in-repo test IdP (S2-05), with `sso.Discover` filling the provider row
from the document the fixture publishes.

**Files:** `api/sso_routes.go` (the routes, the state record, the queue),
`api/sso_routes_test.go`, `api/handlers.go` (mounts `registerSSORoutes` +
`registerIdentityRoutes`, owns `states` and the one clock `SetClock` hands to
state/limiter/ledger), `api/middleware.go` (`RateLimiter.SetClock`, so one clock
covers the whole surface), `store/users.go` (`LinkIdentity`, `ErrIdentityTaken`),
`docs/api.md` (the SSO section as shipped) and `docs/installation.md` §7 (the
redirect URI verbatim, plus the per-knob table of what each does to a login).

**The state is in memory, and the reason is the writer.** Five minutes
(`LoginStateTTL`), consumed by `Take` on the first read, `Prune`d when it expires
unused. A table for it would be written by every unauthenticated redirect — a
request anyone can make — and it would survive the restart that invalidates every
session anyway, because the signing key is ephemeral when `JWT_SECRET` is unset.
The record carries the three secrets only this server knows (nonce, PKCE verifier,
registered redirect URI); single use is what makes a replayed callback a refusal
rather than a second session. `TestSSOStateIsShortLivedAndSingleUse` proves all
three shapes: a state nobody issued, a completed login replayed, and expiry moved
by `SetClock` rather than slept through.

**The redirect URI has one author.** `SSORedirectURI(WEB_URL, provider)` is the
string in the authorize redirect, the string in `GET /api/auth/sso/providers`
(`redirect_uri`), and the string `docs/installation.md` §7 states verbatim — with
the default-ports example `http://localhost:3000/api/auth/sso/oidc/callback`. When
the row carries a different one (an IdP configured for another host), the authorize
route answers `422` with the exact string to whitelist: `invalid_redirect_uri` from
an IdP is the failure this setup produces, and the operator needs the string, not
the symptom.

**The handoff is a fragment, in both directions.** Success:
`${WEB_URL}/auth/callback#access_token=…&refresh_token=…`. Refusal:
`${WEB_URL}/auth/callback#error=<contract reason>&provider=<name>&error_description=…`
(+ `pending_identity=<id>` when the queue row was created). A fragment is not sent
to any server, so the tokens never reach the IdP's logs, our access logs, or a
`Referer`; the test asserts the handoff contains no `?`.

**Refusals keep the contract's vocabulary.** `sso/oauth.go`'s `IdentityError.Reason`
strings are what the fragment carries and what the `sso.login_refused` row records,
with `subject`/`email`/`detail` and `target_user_id`/`pending_identity_id` when the
refusal named an account. The domain-allow-list test is the plan's attack: the IdP
asserts `someone@else.example`, the login ends in `domain_not_allowed`, no session
tokens, no account provisioned, and a ledger row naming who tried to arrive as whom.

**The queue decisions, and what they may not do.** `approve` creates the account the
assertion describes at the **`viewer` floor** and nothing more (`roles == [viewer]`,
asserted). `link` merges the assertion into an existing account, and — the decision
worth stating — `LinkIdentity` **clears the password hash** and stamps
`(provider, provider_id)`: an account whose identity is asserted by an IdP must not
also be openable with a password set before the IdP existed, and S2-06 already
refuses a password login at a provider account, so a hash left in place is a
credential with no path. The store refuses a `(provider, provider_id)` pair an
account already carries (`ErrIdentityTaken` → 409) — there is no unique index on
that pair from Step 1's migration, so the check is inside the transaction that
writes it. A linked account gets `BumpUserGen` + `RevokeAllFor`: every credential
issued before the account became a provider account stops working (asserted on both
the access and the refresh path), its roles are untouched, and the row is audited
with the admin as actor and the account as target. `refuse` requires a reason.
Any decision on a decided row is `409`: the queue is a record, not a form.

`GET /api/identities` is on the admin group, so a `viewer` and an `operator` are
refused with `403 {"error":"insufficient role"}` — and both refusals are ledger rows
under `identity.read` (`refused`), which is what the test counts: one ok read, two
refusals. One action to filter on when an operator asks who touched the queue.

**Test-shape decision:** the fixture's `WEB_URL` is the fixture's own origin. That
is the dev compose's shape — one origin serves the console and proxies `/api` to
the server — so the IdP's redirect back to `${WEB_URL}/api/auth/sso/<p>/callback`
lands on the handler that started the login, and the whole walk is drivable with a
client that refuses to follow redirects (`http.ErrUseLastResponse`), which is the
only way to see the state, the code and the fragment at all.
