# P-16 — "config re-applied on the next camera save" was only ever true of the file

## The finding

The third live-view killer found while closing P-15 (dev stack, wiped volume,
sidecar booted from the seed, origin check open, `/api/ws` answering `101`):
the browser's offer came back

```
{"type":"error","value":"webrtc/offer: stream not found"}
```

while `/api/streams` answered `{}` — even though `/config/go2rtc.yaml` on the
sidecar held the rendered `demo-doorbell` and `demo-doorbell_det` sources, and
re-POSTing that exact file to `/api/config` changed nothing.

Verified against go2rtc master (image `master`, revision `990f4de`, read
2026-11-07): `internal/api/config.go`'s handler for `POST`/`PATCH /api/config`
validates the YAML and `os.WriteFile(app.ConfigPath, data, 0644)` — that is
all. `internal/app/config.go` loads the config bytes into memory once in
`initConfig` at process start; there is no watcher and no reload endpoint.
Streams, listens, and the WS origin check (P-15) are all boot-time. So the
server's `ApplyConfig` (S3-01, pushed on every camera write per S3-05) writes
the sidecar's **next boot** config, and the boot log line's promise that the
"config is re-applied on the next camera save" was only ever true of the file.

The e2e harness had always known — `scripts/e2e-stack.sh` seeds the camera and
then `docker restart`s the sidecar ("the restart below is what instantiates
the streams") — which is exactly the P-12 failure class: the mechanism was
proven against a harness that papered over it, and the dev compose had no
such step, so on a running stack a new camera's live tile stayed dead until
the sidecar happened to restart.

## The fix

A supervisor around go2rtc in both places the sidecar is booted
(`docker/docker-compose.yml`, `scripts/e2e-stack.sh`): seed the config (P-15),
run go2rtc in the background, poll `md5sum /config/go2rtc.yaml` every 2s, and
when it changes — the server just re-rendered it — kill go2rtc and exit 0, so
the restart policy (`unless-stopped`; the e2e `docker run` gained
`--restart unless-stopped` and lost `--rm`, which docker rejects in
combination — `stop` already `docker rm -f`s the container) boots the sidecar
with what the server wrote. A camera save now costs the sidecar a restart
instead of silently never taking effect.

## Exit criteria

- [x] a camera write on a running stack reaches the running sidecar: dev
      stack, `docker compose restart server` → supervisor logs the change →
      fresh boot → `/api/streams` lists `demo-doorbell` with a live producer
- [x] the browser's live tile plays after that chain (Playwright: tile shows
      "last segment …", one clean WS, no `unreachable`)
- [x] the e2e suite passes from a wiped volume twice in a row: `stop` +
      `restart` + `test` → 15/15, 15/15
- [x] the promise the code makes is the promise the file keeps: the compose
      comment states go2rtc never reloads a config in place and names the
      supervisor's cost

## Verification

**Observed 2026-11-07 — dev stack:** after the server's push, sidecar log:
`go2rtc.yaml changed on disk (the server re-rendered it, S3-05); exiting so
the fresh config is booted` → `config path=/config/go2rtc.yaml` →
`/api/streams` = `{"demo-doorbell":{"producers":[{"id":6,"format_name":"h264",
"protocol":"pipe","source":"exec:ffmpeg …"}]}}`. Pre-fix, the same wipe left
`/api/streams` at `{}` through any number of re-POSTs.

**Observed 2026-11-07 — e2e from wiped volumes:** two consecutive
`stop`+`restart`+`test` cycles, 15/15 each. The first cold cycle after the
supervisor landed failed `cameras.spec.ts` twice — a real latent spec bug the
new restart timing exposed (see Notes), fixed in the same commit; the two
green runs are post-fix.

### Mutation evidence

| Mutation | Expected | Observed |
|---|---|---|
| supervisor poll loop removed (seed only) | wiped-volume e2e fails the live spec: streams never register | pre-fix state reproduced during diagnosis: `/api/streams` `{}`, offer → `stream not found` |
| `touch /config/go2rtc.yaml`-equivalent content change on the running dev stack | sidecar restarts within ~2s and re-boots | observed: the server-push chain above is exactly this mutation, fired by the real writer |
| e2e `docker run` without `--restart` | supervisor exit kills the throwaway sidecar permanently, camera seed fails | observed: `--rm` + exit → "the seed camera was not created" |

## Notes

**Cost, stated plainly:** every camera save restarts the sidecar — live tiles
drop (the tile makes one attempt per mount and does not retry, S8-05's
design, so a tile caught mid-restart reads `unreachable` until reload), and
recorder ffmpeg pulls die and respawn on their existing backoff. Camera
writes are rare and operator-driven; the alternative was the feature-sized
one below.

**Rejected — diff-apply via the existing per-stream client:** `client.go`
already has runtime `PUT /api/streams?src=` / `DELETE` (S3-01), which go2rtc
*does* apply live, so `ApplyConfig` could diff the rendered streams against
`/api/streams` and put/delete only what changed — no restart, no tile blink
for unchanged streams. It lost because listens, `api.origin`, and
credentials still cannot be applied live, so the restart path stays
load-bearing anyway, and a correct diff (deletions, source-list equality) is
a feature card's work, not a fix. It remains the better long-term answer if
the blink ever becomes unacceptable.

**Rejected — document "restart the sidecar after camera changes":** keeps the
bug and makes S3-05's boot log line a lie on the stack that prints it.

**The spec bug the new timing exposed** (`web/e2e/cameras.spec.ts`): the zone
test scoped its `saved` assertion with `locator('section').filter({ has:
heading })`, but the camera editor's own `<section>` *contains* the zone
heading, so the filter matched the ancestor too — two `saved` buttons whenever
the camera row happened to be clean at that instant (cold stacks; warm ones
raced past). The comment in the spec already knew about the two-button
problem; the scoping just never excluded the ancestor. Fixed to the heading's
nearest ancestor `section`. This is the same cold-stack family as S8-12's
cleanup race and the P-11 card's note.
