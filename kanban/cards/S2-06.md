# S2-06 — Auth routes: status, login, refresh, logout, profile, password (registration 403)

## Deliverable

GET /api/auth/status {local_login, oidc[]}; POST login/refresh/logout; GET /api/auth/profile; PUT /api/auth/password; POST register answers 403 registration is admin-only.

## Exit criteria

- [x] status answers both buttons the login screen draws, from rows not from env
- [x] login sits behind the rate limiter
- [x] refresh rotates and reuses-detected per S2-01
- [x] registration returns 403 {"error":"registration is admin-only"}

## Notes

Observed 2026-11-03, the card's command verbatim:

```
$ docker run --rm -v $PWD/server:/src -w /src golang:1.26 go test ./api -count=1 -run Auth
ok  	nvr/server/api	1.019s
```

Full suite (`go build ./... && go test ./... -count=1`, `golang:1.26`, module cache
volume): all packages `ok` — `api` 3.348s, `auth`, `config`, `models`, `sso`,
`sso/testidp/provider`, `store`, `ws`. `gofmt -l .` prints nothing.
`server/api/auth_test.go` is 12 tests; the card's `-run Auth` selects all of them.

**The two buttons are read from rows.** `local_login` is
`Users.CountLocalLogin()` — `provider = local AND status = active AND password_hash
<> ''` — so deleting the break-glass admin removes the password form (the test
deletes the admin and asserts `local_login` becomes false). `oidc[]` is
`SSOProviders.ListEnabled()` filtered to `type = oidc`, answered as
`{provider, name, issuer}`. The env flag `BOOTSTRAP_ADMIN_PASSWORD` describes a
boot, not an installation: `config.LocalAdminEnabled()` is kept, but as
`local_admin_seed_asked` in `/readyz`, next to the row-derived `local_admin`. An
operator reading readiness wants both, and the difference between them *is* the
finding.

**Login is the ledger's loudest route.** A failure writes `auth.login_failed` with
the reason the client must not have (`no_such_account`, `account_pending`,
`password_mismatch` in `details`), and answers one 401 — `"invalid credentials"`.
Provider accounts get a 403 with its own words, `"this account signs in through
its provider"`, because the console has to draw the IdP's button, and the
statement names the account's shape rather than its existence. Success writes
`auth.login` (ok) with the method, roles, session id and provider.

**Refresh is rotation with the paper trail S2-01 provides.** The presented row is
closed, the replacement carries `rotated_from = <old token_hash>`. A presented row
that is already closed is `auth.refresh` `refused` +
`401 {"error":"refresh token was already used","live_sessions_dropped":N}`, and
`RevokeAllFor` has already closed the account's live sessions — including the
honest client's new one, which the test proves by refreshing with the replacement.

**The named decision: reuse detection drops sessions, not bearer tokens.** After a
reuse event the access token issued before it still verifies until its 30-minute
expiry (the test asserts `200`, deliberately). Closing a stateless token would
need a per-token revocation list; the design's answer is a short access TTL and
the session revocation. `auth.logout` and `auth.password_change` are the two
routes that do revoke tokens, and they do it by name: `Deny(jti, exp)` plus
`BumpUserGen`, and both effects are asserted — the pre-change access token stops
verifying, the pre-change refresh token stops rotating, the old password stops
working and the new one works.

**Logout takes a body, and the empty body is the loud case.** With
`{"refresh_token":…}` it closes that session (the tab you are logging out of);
with no body it closes every live session of the account and says how many
(`live_sessions_dropped`). "I think my password leaked" is the reason that case
exists, and a console should not have to enumerate sessions to achieve it.

`PUT /api/auth/password` refuses a password under 12 characters with the number in
the message, refuses a provider account with 403 (its password lives at the IdP),
and treats `NVR_SECRET_KEY`-length overflow through `auth.ErrPasswordTooLong` as
422. `POST /api/auth/register` is `403 {"error":"registration is admin-only"}` and
a ledger row, with no account created — the attempt is on the record.

The handler set (`server/api/handlers.go`) is the mount point Steps 3–7 add to, so
every route gets the same gates: the public `/api/auth` group carries the rate
limiter (asserted with a 5/minute budget and a burst of 1 — the second login
guess is `429`), the session group adds `AuthMiddleware`. `server/router.go` now
mounts `api.NewHandlers(ctx, st, nil, nil, cfg).Register(router)`; the hub argument
is nil until the live feed is wired to the recorder, and the handler set mounts
`/ws` only when a hub is handed to it.

Not mounted here, by dependency: the SSO routes (`S2-07`), identities and users
(`S2-09`). The internal worker gate is mounted at `/api/internal/v1` with the
token gate from S2-08, so an empty `WORKER_TOKEN` already answers 403 for paths
that do not exist yet.
