## Notes

**The trigger is the applied signal, not the route.** `applySignal` calls
`broadcastEvent` once, after the store has answered, and switches on
`event.Action` — the action the upsert actually applied, the same value the route
replies with. So the sequence a console sees is exactly the sequence the store
applied, and a signal the store refused (`event closed`, `detection disabled`,
unknown camera) never reaches the wall. Nothing else in the tree sends these three
types; a caller that "also" broadcast would double the storm the throttle exists to
stop.

**The throttle is the hub's, keyed per event, on the leading edge.** It lives on the
`Hub`, not on the caller, because the hub is the thing that decides what reaches every
console at once: a throttle per caller would let two callers each send their own
five-second stream. `EventUpdateWindow == 5 * time.Second` is asserted as a constant,
not just used, and `TestEventUpdateThrottleIsPerEventNotGlobal` is the guard against
the interesting failure — a throttle keyed on something coarser than the event, which
lets one camera's storm silence another's.

**Leading edge is enough because of what the frames carry.** All three types send the
whole event view, and `event.close` is never throttled, so the state an extend loses
to the window is back on the wire within five seconds and the *final* state of every
event arrives with its close. A trailing-edge flush would need a timer per event to
deliver, on the same schedule, something the close already delivers. The storm test
asserts the leading edge explicitly (`signal_count` on the frame that went is the
first extend, not the last).

**A gate is only ever armed by an extend, so the close and the delete both clear it.**
The hub broadcasts payloads it does not parse, so it cannot learn from a close which
id to forget — `ForgetEvent` is the caller's job, called from the close branch of
`broadcastEvent` and from `DeleteEvent`. The belt for a caller that forgot (a restart,
a row deleted by hand) is eviction: an allowed send for any id drops gates untouched
for `gateStaleAfter` (1 h), and the sweep runs for *new* ids too — the event that
closed while nobody was watching is exactly the one that would otherwise sit in the
map forever. The map therefore stays the size of the events open right now.

**An update with no event id is sent, not dropped.** One global window shared by every
event is the bug the throttle exists to prevent, and silently dropping a frame nobody
can attribute is worse than sending one.

**The clip assembly is the one fact about a closed event that still moves, and it
lands on a timer rather than in a request.** `ClipBuilder.OnAssembled` hands the
finished row to `Handlers.BroadcastEventUpdate`, wired in `main.go`. It is a callback
rather than a hub reference because this package must not own the message shapes: what
the console receives is the event view, and the view belongs to the API. The callback
fires for the empty-window case too — "there will be no clip" is the answer a waiting
player needs — and never when the row is gone, so a deleted event does not put a card
back on a wall that just removed one. The in-memory row is brought in line with the
write before the callback, so the payload carries the clip rather than the state from
before it.

**The payload is the list view, whole.** `viewEvent(ev, refs, false)` — the same view
the list and the drawer answer — so zones arrive by the name the operator drew rather
than the id the row stores (the S6-04 rule: the camera row is the only place the
id↔name pair exists, and the console has never been given the id). `has_snapshot` and
`has_clip` ride along, which is what makes the third criterion true rather than
aspirational: a card can be drawn, coloured and given a player without a REST call.

**The console in the API suite is a real WebSocket, not a spy on `Hub`.** A spy proves
the call is made; it does not prove the frame arrives, in order, with a payload that
can be drawn. `newLiveConsole` dials `/ws` against the same handlers the signal route
uses and waits for `hub.Count() == 1` before any signal is posted — a broadcast sent
inside the registration window goes to the consoles that are connected, which is none
of them. Presence frames are skipped on purpose: a test waiting for `event.new` must
not mistake a join for an event.

**Reading of the third exit criterion.** "An open event shows LIVE in the console from
these messages alone" is verified here as the server's half: the frames carry id,
camera slug, the running window, classes, zone names, severity, signal count and the
media flags, asserted by decoding the payload that arrived on a real socket, with no
REST call in sight. The console that draws it is `S8-10` (`realtime.ts`), still
backlog; when it lands, this is the contract it renders against.

**Deviations from the card's `paths`.** The card named `server/media/clips.go` and
`server/ws/hub.go`. The fan-out also needed `server/ws/hub.go`'s throttle type, the
trigger in `server/api/detector_api.go`, the payload builder and `ForgetEvent` call in
`server/api/events.go`, and the assembler wiring in `server/main.go`. `handlers.Hub`
already existed (S2-10 mounted it), so no handler field was added — every broadcast
site nil-checks it, because a process built without the live feed is a stated state
and the hub-less fixture is what every other suite in `api` uses.
