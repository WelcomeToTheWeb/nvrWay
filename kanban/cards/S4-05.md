## Notes

What the card's one line left open, and what the code decided:

- **The window is overlap, not containment.** `Segments.ListRange` (S1-10) answers
  `end_ts > from AND start_ts < to`, and the route keeps that meaning: a segment
  crossing either edge is in, a segment merely touching it is out. It is the clip
  builder's rule (S6-01) for the same reason — a scrub that starts mid-segment
  needs that segment, and hiding it shows a hole where the footage is.
  `TestSegmentsWindowIsOverlapNotContainment` pins all four edge cases.
- **A request naming no window gets the server's.** `to` is `h.now()` and `from` is
  `to - DefaultManifestWindow` (1 h), and the response answers `from`, `to`,
  `limit` and `truncated` so the caller can see what it was given. The plan's
  `scripts/verify.sh` gate 6 asks for `?camera_id=<id>` and nothing else, so a
  required window would have pushed date arithmetic into the gate and into every
  console screen. An hour at the plan's 5 s segment is 720 rows, inside the 2000
  ceiling.
- **`[]` for an empty window, 404 for a camera that does not exist.** "Nothing was
  recorded then" is an answer about the property and the scrubber draws a gap; a
  `camera_id` naming no row is a request about a thing that is not there. The 404
  reuses the camera route's own words, `no camera with that id`, so one wrong id
  reads the same in both places. The empty answer is asserted on the bytes —
  `"segments":[]`, not `null` — because a console iterates what it is handed.
- **The limit is the store's ceiling, and its effect is stated.**
  `store.SegmentListMaxLimit` (2000) is the cap; a larger request is clamped and
  the clamped number is what the response names. `truncated` is decided by asking
  for `limit + 1` rows and seeing whether they arrived, so "the window held more"
  is an observation rather than a guess from a count that happened to land on the
  cap.
- **The row shape is the scrubber's, not the disk's.** `id`, `camera_id`, `slug`,
  `generation`, `start_ts`, `end_ts`, `seconds`, `bytes`, `kind`, `uploaded`. No
  `path` — that is a name on this server's filesystem, and playback is
  server-proxied (S6-05), so the row's `id` is the handle. `slug` is present
  because a manifest spanning cameras cannot ask for it per row; a segment whose
  camera row is gone answers with an empty slug rather than losing its footage.
  `uploaded` is there because the local tree is a working copy, and a strip that
  has not been pushed off the box is one the operator should know is still only
  here.
- **`viewer` floor, and no ledger row.** The read group carries only
  `AuthMiddleware`, matching `GET /api/v1/cameras`: reading footage is the lowest
  thing a signed-in account can do. Reads of this route are not audited — the
  ledger records acts (S2-08) and the console polls this route — which is why
  there is no `segments.read` verb in `deniedActions`; a refusal here can only be
  a 401, which has no actor to name.
- **`docs/api.md`'s Segments section is still the S0-02 stub.** Step 3 left its
  section a stub for the same reason (S9-10 fills the route tables); the shape is
  pinned here and in the suite until then, so the doc has something to copy.
