# P-11 — the strip shows the event's window; the clip reaches past it, and the console cannot say by how much

## Deliverable

`media.ClipBuilder` cuts a clip from the event's window **plus**
`PRE_ROLL_SECONDS` before and `POST_ROLL_SECONDS` after (S6-01), and the recorder
starts and stops on the same rule. So the footage an operator can watch is wider
than the event's `started_at`…`ended_at`, and the drawer's segment strip — which
asks `GET /api/v1/segments?camera_id=&from=&to=` for the event's own window —
draws a narrower band than the clip it sits under.

S8-06 shipped the honest version: the strip is labelled with the window the
**server echoed** (never this browser's clock) and says outright *"the clip may
reach past this window, because the server pads it by the roll settings and this
console is not told them"*. That sentence is true on every installation and useful
on none — an operator cannot tell whether the clip starts 8 s earlier or 30.

## The choice: `GET /api/v1/settings/media`, read by both readers

**Option 1 won, as a new route rather than an extension of the retention one.**
`GET /api/v1/settings/media` (mounted beside `/live` on the plain read gate —
any signed-in role) answers `pre_roll_seconds`, `post_roll_seconds`,
`segment_seconds` from the same `Cfg` fields the clip builder and the recorder
read in the same process, so the screen and the ffmpeg arguments cannot
disagree. The drawer fetches it, pads the segment request with
`clipWindow(event, roll)` (started − pre, ended + post; an open event pads its
start and still names no end), and the caption now names the window it drew:
*"the window the clip was cut from: 8s of pre-roll before the event, 15s of
post-roll after"*. The retention panel reads the same door for the same three
numbers, so criterion 3 holds: one setting, one answer, two readers, and the
panel restates no default.

Why not the retention route for these numbers: it is mounted on the **admin**
group, and the drawer is a viewer's screen — a viewer must be able to pad their
own strip. One route serving both readers had to sit at the lower gate, and
`settings/retention` cannot move down without leaking the sweep policy.

**Option 2 (`clip_from`/`clip_to` on the event view) lost** as the card said:
the exact truth for one drawer and nothing else — the retention panel would
still need the roll itself (the env names them, not the event), and
`segment_seconds` would have no door at all.

**Option 3 (a pad query parameter) lost in advance**, as pre-rejected: a
server-side policy moved into a parameter every page would have to remember.

Failure direction, stated: if `settings/media` cannot be read, the strip falls
back to the event's own window **and keeps the old apology sentence** — an
unpadded band that admits it is not told the roll, rather than a band padded
by a number the console invented. That is the card's own temptation paragraph
made a tested behaviour.

## Notes

Found 2026-11-06 while building S8-06's strip. The temptation was to pad the
request by a constant the console invented — 30 s, say — which would be right on
the plan's defaults and wrong on any installation that changed them, and would
look like evidence. The strip's whole job is to say which footage exists; a band
drawn at a guessed width is worse than a narrower band that says what it is.

Related: `GET /api/v1/settings/live` (S8-04) is the precedent for this shape —
one small public settings route so the console never hard-codes a server value.

Deviation from the card's first option sketch: it suggested
`settings/retention` *or* `settings/media`; what shipped is `settings/media`,
because the retention route is admin-mounted and the drawer needs the answer at
the viewer gate. The retention panel then reads *two* routes — its own admin
one for the sweep windows, the new one for the roll — which is still one answer
per number.

Cold-start note: the first e2e run after `restart` failed
`cameras.spec.ts:78` (the cleanup test) once; the next two runs were 15/15.
P-11 touches no camera path; this is the cold-stack race S8-12's card already
documents (in-flight recorder bookkeeping against the delete on a just-booted
server), recorded here rather than hidden.
