## Notes

**Done 2026-11-04.** `server/api/storage.go` is the surface the Settings page
and `scripts/verify.sh` step 7 drive: ten admin routes over the backends, the
connection test, and the queue. Sixteen tests in `./api -run Storage`; `docs/api.md`'s
storage section is now the real contract rather than a note to write one.

**A secret has no path out, and the test proves it in the strongest form.** Not
"the view has no secret field" but *the bytes of every response do not contain
the secret* — which also catches a handler that puts one in an error message. The
view carries `secret_set` (the plan's field) **plus one flag per column**
(`password_set`, `access_key_set`, `secret_key_set`, `private_key_path_set`),
because the form has one field per column and needs to know which already hold
something. `private_key_path` is write-only too: which key file an installation
uses is information. The suite also reads the column back and asserts it is
sealed text that opens with this installation's key — the route seals, and the
store never sees plaintext.

**An omitted secret and an explicitly empty one are different acts.** Omitted
keeps what is stored (which is what lets the console round-trip a row whose
secrets it cannot read back); `{"password":""}` clears it. The pointer is what
tells them apart. The first version read the store's four seal flags off the row
*after* sealing, which lost the one case that matters: a cleared column is empty,
so "is it non-empty" said "do not write it" and the old secret survived the
operator deleting it. The flags now come from what the payload **sent**, and
`TestStorageUpdateKeepsAnOmittedSecretAndClearsAnEmptyOne` drives both. It also
means the ledger records the clears — "the password was removed" is exactly what
a ledger row is for.

**The API validates presence, the driver validates shape.** A missing bucket or
an `fs` row with no `root_path` is a 422 naming the field, because that is the
moment the operator is looking at the form. What an endpoint may look like,
whether a prefix repeats the endpoint's path, whether a WebDAV container is the
first segment — the driver's call, made at open, with the test route carrying the
answer. Duplicating the driver's grammar here would give one rule two authors,
and they would drift the first time a driver learned something new.

**One trap in that split:** `models.KindNeedsRoot` is true for **both** `fs` and
`sftp`, because both write under a root — it is not a statement about being
*addressed* by one. A switch that asked "does this kind need a root?" before
asking which kind it is demanded a host:port from a directory, and every `fs`
backend failed with "endpoint is required for a fs backend". `fs` is now checked
first, and the comment says why.

**The connection test answers with one of four names, verbatim**, because they
are the storage package's sentinel messages and not a table in this file — there
is no second place for them to drift. Three of them are driven through the route
here: a missing directory (`bucket missing`), an endpoint that refuses the
connection (`discovery_unreachable`), and an in-test S3 stub that answers 403
(`bad credentials`) and 404 (`bucket missing`). The fourth,
`sftp host key changed`, is produced by the sftp driver and asserted verbatim in
`storage/sftp_test.go`; what this file proves is that the route prints whatever
name the storage package produced, unchanged.

**A refusal with no name among the four answers `connection_failed`**, with the
driver's sentence in `reason`. That is not a fifth tier state — it is the honest
absence of a name. The case an installation actually hits is `ErrBadKey`: the
credential was sealed by a different key, so the server and the credential may
both be fine and only this process cannot open the row. Inventing a fifth name
would make the console draw a tier problem where the fix is an environment
variable.

**Saving does not test the tier.** An S3 endpoint that is briefly down must not
stop an operator adding a second destination, and the installation keeps
recording to the others meanwhile. The test route is the explicit act. (The OIDC
surface does the opposite — discovery runs at save — and the difference is real:
an issuer that has never answered discovery has never been configured correctly,
while a bucket can be unreachable for ten minutes.)

**`kind` cannot change on an existing backend.** The sealed columns a row carries
mean something different per kind, so re-shelving an s3 row's credentials onto an
sftp row would leave secrets that mean something else. 422, with the fix in the
message: delete it and add the other one.

**No backend is the default until an operator says so.** The plan's example body
sends `is_default: true` explicitly, and auto-flagging the first row would leave
it flagged after a second arrives. What the installation still resolves is the
store's fallback — with one enabled backend and no flag set, that backend *is*
the default — and the test asserts that resolution rather than a flag that was
never set. `PUT …/default` refuses a disabled backend: the default is where the
queue puts things, and a disabled backend takes nothing.

**`PUT …/enabled` answers with `is_default` as well as `enabled`**, so the
console can say "you just disabled the default destination" without a second
request. The route's semantics are the uploader's: a pause, not a cancellation,
and jobs already claimed finish because the claim is the gate.
`TestStorageDisableStopsNewClaims` drives the plan's verify step 7 through the
store's own `ClaimNext` rather than trusting the flag.

**Queue pagination follows the event timeline's rule.** The page is asked for at
its limit and a full page probes the next offset, because the store clamps its
limit at 200 — asking for `limit+1` would answer `truncated: false` at exactly
the ceiling, which is a queue page that looks complete where it is cut. `counts`
is the whole queue, not the page: the headline number is "what is stuck", and a
page of 50 out of 4000 would otherwise report four. A `state` that is not one of
the four answers 400, not an empty page.

**The queue names its backend.** `backend_name` comes from one read of the
backends table per page, not one per row: a queue of uuids is a page no operator
reads, and a row whose backend was deleted answers the empty string, which is
itself the answer.

**`DELETE` reports the queue rows it orphans** and leaves them. The store's
comment says the handler answers that question, and the answer is a number:
"the queue is not moving" is a question whose answer is a count, and deleting the
rows behind the operator's back would hide the fact.

**One driver change fell out of the prefixes route, and it is the right one.**
`fs.List` answered an unmounted root with an empty list. A prefix with nothing
under it *should* answer empty — that is what "this path has no footage yet"
looks like before the first recording lands — but a root that is not there means
the mount is not there, and an empty list is exactly what a wrong prefix looks
like. `s3` already refused a missing bucket, so `fs` now refuses a missing or
non-directory root with `bucket missing`, and
`TestFSListRefusesARootThatIsNotThere` pins both halves of the distinction.

**Two model constants added** (`storage.backend_read`, `storage.backend_prefixes`)
and the seal key is derived **once** in `NewHandlers` rather than per request:
`config.SealKey` warns when `NVR_SECRET_KEY` is unset, and a route that
recomputed it would fill the log with the same warning on every Settings page
load. An unusable seal key is a 500 that says so, on the write paths and the
open paths alike.
