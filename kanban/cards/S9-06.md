# S9-06 — the GPU card that was blocked on hardware that quietly arrived

## The finding

The card sat `blocked` on a true sentence written 2026-11-01: "Docker with
runc only, no nvidia-container-toolkit, no /dev/nvidia* nodes." S3-08 landed
the host fix on 2026-11-02 and the block was never re-checked — until S9-10's
close demanded stating the GPU gap honestly and the re-probe answered
`providers=CUDAExecutionProvider,CPUExecutionProvider` and "GPU is reachable
from this box" (RTX 4070 Laptop, driver 615.78.08, toolkit 1.20.1). A blocked
card is a claim about the world; this one had gone stale.

## The fix

**`docker-compose.gpu.yml`** (repo root): detector-only overlay — device
reservation (`driver: nvidia, count: all, capabilities: [gpu]`),
`NVIDIA_VISIBLE_DEVICES=all`, `NVIDIA_DRIVER_CAPABILITIES=compute,utility`,
`DET_PROVIDERS=CUDAExecutionProvider,CPUExecutionProvider` (CPU stays in the
list: a worker that cannot open CUDA falls back and warns, it does not die).
Carries a complete `build:` section so both stacks build the GPU image — the
CUDA variant is not published to ghcr (~2 GB of wheels; the CPU image is the
baseline every install gets).

**`docker/Dockerfile.detector` stage 3 (`runtime-gpu`)**: same worker, model
and entry point; swaps `onnxruntime` for `onnxruntime-gpu==1.31.1` plus the
CUDA libraries the provider dlopens — `nvidia-cudnn-cu13`,
`nvidia-cuda-runtime`, `nvidia-cufft`, `nvidia-curand`, `nvidia-cusolver`,
`nvidia-cusparse`. Three traps, all hit and documented in the Dockerfile:
the suffixed `-cu13` names are 0.0.1 PyPI placeholders (CUDA 13 consolidated
to unsuffixed wheels); missing one degrades the session to CPU with only an
ORT-internal warning; and the pip layers need `USER root` (the runtime stage
ends as `nvr`). `ldd libonnxruntime_providers_cuda.so` is the checklist — its
only remaining `not found` is `libcuda.so.1`, the driver library the toolkit
injects at runtime, which must never be pip-installed.

**The last-stage bug this card introduced and fixed**: making `runtime-gpu`
the final stage silently made it the *default build target* — the first
`compose build` tagged the 2 GB CUDA image as `nvr/detector:latest` and the
suite noticed (a CPU-build test saw CUDA in `get_available_providers()`).
The base compose now pins `target: runtime` explicitly; the overlay overrides
to `runtime-gpu`.

**Worker honesty (`model.py`)**: the startup line printed the *requested*
providers. With the CUDA wheel present but no GPU reachable, onnxruntime
opens the session anyway, runs CPU, and warns only on its own logger — the
log claimed CUDA forever on a box inferring on CPU (observed directly:
`ACTIVE_AFTER_OPEN=CUDA,...` with no GPU process in `nvidia-smi`). `_open`
now reconciles against `session.get_providers()`: the active list is what the
worker reports, and a silent substitution gets a worker-level WARN. Three
tests in `detector/tests/test_providers.py` pin it.

**Docs**: installation.md § 12 rewritten from "does not exist yet" to shipped
+ verified (commands, what to expect in the logs, the fallback rule, the
verified host's facts, and the claim that remains open — performance at
scale); architecture.md Inference-host section rewritten to the same posture;
the "Gaps v1 leaves open" section now lists two gaps and records GPU
verification as closed; README's baseline bullet updated. These are the
edits S9-10's Notes assigned to this card.

## Notes

The blocked→unblocked path is the durable lesson: `scripts/gpu-probe.sh
--cuda` is cheap and definitive, and any card blocked on hardware should
re-run it before its next status change. The dev stack now runs the GPU
worker by default on this box (`up -d` with the overlay); the CPU image
remains what a fresh install gets.
