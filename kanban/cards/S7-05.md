## Notes

**Done 2026-11-04.** `server/storage/webdav.go` is the `webdav` driver: gowebdav
against a share, with the first path segment of the row's prefix treated as the
bucket. 19 tests (35 with subtests) in ./storage -run WebDav; whole suite,
`go vet ./...`, `-race` and `gofmt -l .` green.

**The plan's API names are from an older gowebdav.** v0.13.0 exports no
`Writer()`, `ReadCloser()` or `Propfind()`. What the driver uses instead:
`WriteStreamWithLength` (Put), `ReadStream` (Get), `Stat`, `Remove`, `ReadDir`
and `Connect`. The plan's `Propfind(path, 0)` is doubly wrong for `List`: the
function is unexported, and Depth 0 describes only the resource named — a
listing needs Depth 1, which is exactly what `ReadDir` sends.

**`List` is therefore a walk, and the recursion is the driver's.** One PROPFIND
Depth 1 per collection, descending into each child that reports
`resourcetype/collection`, bounded at 32 levels because a WebDAV server is
somebody else's filesystem and a loop there should cost an error rather than the
process. A collection that is not there is an **empty list, not a failure** —
the sweeper asks about a day before the first upload of that day has ever
happened.

**MKCOL's 405 is not a failure, and that is the library's doing.** RFC 4918 says
MKCOL on an existing resource is 405, and gowebdav's `mkcol` answers it with
`if status == 405 { status = 201 }` (`requests.go`). So its streaming writes —
which build the parent collections *before* the PUT, rather than s3's "PUT, and
make the parents if it 404s" — are safe against a correct server, and `Put` may
stream instead of buffering. `TestWebDavMKCOL405IsNotAFailure` pins it from both
sides: the in-test server really does answer 405 (it is written to the RFC, not
to the client), and the upload still lands. This is worth a test precisely
because the RFC reading says the opposite, and the wrong conclusion would have
put every uploaded object in memory — the first draft of this driver buffered,
for exactly that reason.

**The endpoint is a URL here, not a host, and the scheme is required.** s3
decides TLS with one checkbox and strips any scheme from the endpoint; a WebDAV
endpoint is a URL and `http://` on a LAN share and `https://` on a hosted one are
both correct, so a bare `nas.local:5005` is refused as ambiguous rather than
guessed. A user in the URL is refused too — gowebdav would ignore it while the
form showed a username field. A prefix that repeats the endpoint's path is
refused: Nextcloud serves at `/remote.php/dav`, and putting that in both fields
sends it twice.

**The endpoint's own path must survive into every request.** gowebdav appends
object paths to the root URL, so everything handed to the client is a path
*within* that root — pass it a URL and it is concatenated onto itself. The first
draft built the object path from the endpoint URL and produced
`PUT /media/media/…` for a prefix of `media`; `TestWebDavEndpointPathIsPartOfEveryRequest`
holds a share mounted under `/remote.php/dav` to keep the split between the URL
(the root) and the path (the object) from being merged again.

**No Content-Type is sent on a PUT, deliberately.** gowebdav's `SetHeader` writes
into a per-*client* map that is replayed on every request and can only be added
to, never removed — so setting it around an upload would leak the type into
unrelated requests and race between concurrent uploads. A WebDAV server derives
the type from the name (Apache, nginx and Nextcloud all do), `Stat` reads back
whatever it settled on, and the extension is the fallback when the share reports
nothing. `TestWebDavStatReportsTheServersTypeAndTheExtensionIsTheFallback`
asserts all three rungs: the share's type wins even when it disagrees with the
extension, and the extension decides only when the share is silent.

**The container is the prefix's first segment, and `Ping` checks it.** OPTIONS
says the thing is a WebDAV server and that the credential is good; the PROPFIND
on the container is what catches a share that answers without the directory the
operator named — `bucket missing`, naming the collection. A share with no prefix
has no container to check, and `Ping` stops at OPTIONS.

**The four names, and one thing that keeps its own.** 401/403 → `bad
credentials` (asserted for a wrong password *and* a wrong user, over the wire,
through gowebdav's own auth negotiation); 404 on an object → `ErrNotFound`,
which is not one of the four; 409 → `bucket missing` (the parent collection is
not there and could not be made); a dead share → `discovery_unreachable`; an
unverifiable certificate → `discovery_unreachable` **with "x509" kept in the
message**. A 507 from a full NAS keeps its number and maps to no name: it is
neither a credential problem nor a connectivity one, and inventing a name for it
sends the operator to the wrong settings field.

**A second delete is silent, like S3.** gowebdav's `Remove` answers success for a
404, so the shared contract's refusal to require `ErrNotFound` from a second
delete is right for two of the four kinds already. Recorded, not relied on — the
sweeper clears `remote_key` either way.

**The password never appears in a line this process writes**, asserted on both
the returned error and the standard logger's output. The username may: it is not
sealed, and the plan's rule is that a username is not a secret in the sense the
seal is about.

**The prefix-is-honoured assertion is structural.** The contract test checks that
every request the share saw is at or under `/media` (OPTIONS excluded, because
`Ping` probes the share root) rather than comparing against the contract's own
key spelling. That choice came out of a chase worth writing down: the assertion
failed while both sides *looked* identical, and the bytes settled it —
`contract_test.go` holds `contract/2026/11/04/front-door-0.mp4` and the tool
output rendered it as `2026-11-04`. **When a string comparison fails and both
sides look the same in the transcript, dump the bytes (`od -c`); the display can
be lying.**
