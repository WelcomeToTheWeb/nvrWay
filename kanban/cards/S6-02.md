# S6-02 — Snapshot write: decode signal snapshot_base64 to <SNAPSHOTS_DIR>/<event_id>.jpg

## Deliverable

open-signal snapshots land on disk and set LocalSnapshotPath; the 250 KB rule and the absent-snapshot case are honored.

## Exit criteria

- [x] snapshot written only on open
- [x] missing snapshot leaves the event visible; the route names the absence (`404 {"error":"snapshot not available"}`) — the `snapshot_url` field that says "no picture" in a list is S6-04's view
- [x] the file is served by GET /api/v1/events/:id/snapshot

## Verification

`docker run --rm -v $PWD/server:/src -w /src golang:1.26 go test ./api -count=1 -run Snapshot`

(the seeded card named `./media`; see the package deviation below)

## Notes

**Done 2026-11-04.** The picture an event was detected on is written by the
signal path, filed at `<SNAPSHOTS_DIR>/<event_id>.jpg`, stamped on the row as
`local_snapshot_path`, and now served by
`GET /api/v1/events/:id/snapshot → image/jpeg`.

**Package deviation (2026-11-04), the same shape S6-03 recorded.** The seeded
card named `server/media/clips.go` for the write and `./media -run Snapshot` for
the proof. The write is not in `media`: S5-10 put it in the signals handler
(`api/detector_api.go:writeEventSnapshot`), because the snapshot arrives on a
signal and the handler is the thing that decodes base64 and owns the row. The
route is `server/api/events.go`. Paths and Verification are re-pointed at
`./api`; the deliverable is unchanged.

**The write guard changed, and that is the only behaviour this card altered.**
S5-10 wrote the snapshot when `created && action == open && snapshot_base64 != ""`.
`created` is the wrong gate: a worker re-sends an `open` because it did not hear
the answer, and if the first attempt lost the picture — over the cap, a disk that
refused the write — the replay lands on an existing row, `created` is false, and
the event goes down in history pictureless because of one bad attempt. The gate
is now **"this row has no picture"**:

```go
if s.Action == models.SignalActionOpen && s.SnapshotBase64 != "" && event.LocalSnapshotPath == "" {
	h.writeEventSnapshot(event.ID, s.SnapshotBase64)
}
```

That keeps both rules the criterion cares about: only an `open` ever writes
(`TestSnapshotIsWrittenOnlyOnOpen` — an extend and a close that carry a picture
write nothing, so a five-minute loiter cannot replace its own evidence), and a
replay fills a missing picture without ever overwriting one that exists
(`TestSnapshotReplayedOpenFillsAPictureTheFirstAttemptLost`,
`TestSnapshotReplayDoesNotOverwriteAPictureThatExists`).

**Two hygiene changes in the same function.** The name is built with
`filepath.Base(eventID)` and the file is written `0o640` like the recorder's
segments — a picture of someone's property, read by this process and nobody else
on the box. `Base` is what makes the route's containment guard satisfiable.

**The route.** `registerEventRoutes` mounts `GET /api/v1/events/:id/snapshot`
behind `AuthMiddleware(h.JWT)` alone — every authenticated role reads events, and
a read is not an act, so there is no ledger row and a 401 has no actor to name
(the same reasoning S4-05 recorded for the segment manifest). Three answers, each
named, because the console draws each in a different place:

| Answer | When |
| --- | --- |
| `200 image/jpeg`, `Cache-Control: private, max-age=3600` | the picture, byte for byte |
| `404 {"error":"event not found"}` | no such event |
| `404 {"error":"snapshot not available"}` | the event stands, without a picture |

The last row covers three situations that all mean the same thing to an operator:
the signal never carried one, it was over `MaxSignalSnapshotBytes` (250 KB), or
the file is gone (the sweeper's local delete, S7-09). The plan's rule for the
clip — a named 404 for events whose media is gone — is applied identically, and
the event's own row is untouched in every case. `http.ServeContent` rather than
`ServeFile` is what answers a `Range` request (206) and a conditional GET, and
the cache promise is safe because a picture is written once and never rewritten.

**Containment.** `snapshotIsInPlace` refuses any path that is not under
`SNAPSHOTS_DIR` after both sides are made absolute: a row restored from another
installation must not turn the snapshot route into a general file reader
(`TestSnapshotRouteRefusesAPathOutsideTheSnapshotDir`).

**The v1 gap, stated rather than hidden.** A snapshot whose local file is gone
but whose `snapshot_uploaded_at` is set lives on the storage tier, and this route
answers the same named 404: reading a remote object needs Step 7's `Backend`
interface (S7-01), exactly as the clip's remote seek does (S6-05). It is the
documented v1 limit, not a missing branch.

**The S6-02 / S6-04 boundary, so the two cards do not re-litigate it.** This card
lands `server/api/events.go` with the snapshot route and the shared `eventByID`
lookup, and nothing else. S6-04 adds `GET /api/v1/events` (the filters),
`GET /api/v1/events/:id`, `DELETE /api/v1/events/:id` and the view fields —
including `snapshot_url`, which is where "this event has no picture" becomes a
field a list can draw. S6-05 owns `GET /api/v1/events/:id/clip`. The read gate is
already the one all four need.
