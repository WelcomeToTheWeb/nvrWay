**The card's shape was copied from OurWay's, and three parts of it had to change**, because the server this console talks to is not OurWay's. All three come from one fact in `server/api/auth.go` `Refresh`: a refresh token is **stateful and single-use**. The presented token is closed, the replacement is recorded in `rotated_from`, and presenting a closed token is *reuse* — `401 {"error":"refresh token was already used","live_sessions_dropped":N}` with **every live session of the account dropped**.

1. **The rotated refresh token is stored.** OurWay's `client.ts` does `localStorage.setItem('ourway_access_token', data.access_token)` and nothing else; its `context.tsx` `refresh()` does the same. Copied here, the next renewal would present a token the server already closed, and opening a page would log the operator out of every device. `saveTokens(access, refresh)` takes both halves and cannot be called with one.
2. **Renewal is single-flight.** Not in the card, not in OurWay, and not optional. THE WALL mounts and asks for cameras, events, segments and storage at once; six concurrent 401s posting six refreshes means one rotation and five replays. Concurrent 401s now share one `renewal` promise.
3. **`AUTH_EXEMPT_PATHS` — `/auth/status`, `/auth/login`, `/auth/refresh`.** A 401 from `POST /api/auth/login` is `{"error":"invalid credentials"}`, an answer about the credentials just typed, not about this browser's session. S8-03's LoginPage has to receive it to say why the sign-in failed; renewing there would rotate a healthy session for nothing and send the operator to a login page that no longer explains anything.

**Deviations from OurWay's `context.tsx`, each with the reason:**

- **No background refresh timer.** Ours has none; OurWay renews on a 5-minute `setInterval`. `models/session.go:78` sets `AccessTokenTTL = 30 * time.Minute`, so the timer is 6× more eager than it needs to be, and a timer in *every tab* is a reuse-detection machine — two tabs, one rotation, one replay, all sessions dropped. The 401 path renews on demand at no cost the operator sees.
- **Roles are read from `user.roles`.** OurWay reads `data.roles` from the login response and `res.data.user` / `res.data.roles` from the profile. nvrWay's `userView` (`api/handlers.go:321`) carries roles *inside* the user object and both routes answer the user object directly; the copied reads would have stored `undefined` into `nvr_roles`.
- **`logout()` tells the server first** — `POST /api/auth/logout` with the refresh token, which closes that one session (`api/auth.go` Logout). OurWay's logout only clears localStorage, leaving a refresh token valid for `RefreshTokenTTL = 14 days` on a machine that still holds it. The local state is cleared whether or not the server answers; a console that stayed signed in because the box was unreachable would be lying about the door.
- **No `register()`.** `POST /api/auth/register` is `RegisterDisabled` and `GET /api/auth/status` answers `registration: false`.
- **No read throttle, rate-limit backoff, or client-scope header.** OurWay's `client.ts` carries ~120 lines of that: a 4-deep GET queue sized to its limiter, a 60 s 429 backoff, and an `X-OurWay-Client-Scope` capture. All three are RMM machinery for a polling dashboard with ten thousand units; no nvrWay card claims them, and unclaimed machinery in the one file every request passes through is a liability, not a head start.

**File added beyond the card's `paths:`** — `web/src/auth/session.ts`. Four key names with three writers (the client clears them, the context writes them on sign-in, the SSO callback writes them from a fragment) is three chances for a literal to drift. It also breaks what would otherwise be an import cycle: `context.tsx` imports `client.ts`, so the key names cannot live in `context.tsx`.

**Test harness: a custom axios adapter, not the tools the exit criterion names.** The criterion says `vi.stubGlobal('fetch')` / axios mock adapter; the *assertion* is the requirement and the parenthetical names means. Probed in this environment: `axios.defaults.adapter` is `["xhr","http","fetch"]` and `XMLHttpRequest` is a function in jsdom, so the **xhr** adapter wins and `fetch` is never consulted — stubbing it would intercept nothing. `axios-mock-adapter` would be a new dependency outside the plan's pinned set. A test-local adapter sits at the bottom of the real pipeline, so every assertion below is about requests the interceptors actually produced.

**The tests were mutation-checked, because a test that cannot fail proves nothing.** With the single-flight guard removed, exactly the two concurrency tests fail and the other twelve pass (`renews once for a burst of concurrent 401s`, `shares one failed refresh across a concurrent burst, and logs out once`). With OurWay's token shape restored — `saveTokens(data.access_token, readRefreshToken())` — exactly one fails: `expected 'old-refresh' to be 'new-refresh'`. Both mutations were reverted and the suite re-run green.

**Harness fix, not a product fix** — `web/src/test/setup.ts` now installs a Storage-shaped store when the host's is unusable. Node 26 defines a `localStorage` global of its own (experimental web storage) that shadows jsdom's on `globalThis` and, without `--localstorage-file`, warns and returns `undefined`: `(node:29090) ExperimentalWarning: localStorage is not available because --localstorage-file was not provided`, with `window.localStorage === undefined` and `window === globalThis`. Every session assertion in this card is about what lands in that store, so the harness supplies the storage a browser provides. It is installed only when `localStorage.getItem` is not a function, so a runtime with a working one keeps it. Related host facts are in the S8-01 card (Node 26 / npm 11, `vite preview` binding `[::1]`).
