# S2-02 — auth/argon2.go: password hash + verify

## Deliverable

argon2id hash/verify via golang.org/x/crypto/argon2, used by the break-glass admin and PUT /api/auth/password.

## Exit criteria

- [x] hash encodes params + salt in the stored string
- [x] verify is constant-time and false on mismatch
- [x] params recorded in the card/commit (they are a decision, not a default)

## Verification

`docker run --rm -v $PWD/server:/src -w /src golang:1.26 go test ./auth -count=1`

## Parameters (the decision, recorded)

argon2id, PHC string `$argon2id$v=19$m=65536,t=3,p=4$<salt>$<hash>`, base64
without padding:

| parameter | value |
| --- | --- |
| time | 3 passes |
| memory | 65536 KiB (64 MiB) per hash |
| threads | 4 |
| key length | 32 bytes |
| salt length | 16 bytes, system CSPRNG, random per hash |
| password bound | 1024 bytes, refused before hashing |

Why these: 64 MiB with 3 passes is the OWASP argon2id shape (its minimum point is
t=2, m=19 MiB, p=4). nvrWay hashes at a rate limiter's pace — a login inside
`RATE_LIMIT_PER_MINUTE` (120/min default), a password change, the break-glass
seed — which is roughly a tenth of a second of CPU per hash on commodity
hardware: invisible to the person typing, ruinous for someone holding a stolen
password list. argon2id, not argon2i: the hybrid is the mode that resists both
the time-attack and the GPU-cracking family.

`NeedsRehash` is why the parameters can move later: verify recomputes under the
parameters the stored string names, and the login path rewrites the hash when
they are not the current ones. No account is locked out by a parameter change.

## Notes

`server/auth/argon2.go`: `HashPassword`, `VerifyPassword`, `NeedsRehash`, the
parameter constants, and `PasswordMaxBytes` (argon2's cost is independent of
password length, but the password is copied into the hash — an unbounded
password is an unbounded allocation).

The stored string is the PHC format, so parameters travel with the hash and a
hash written under older parameters still verifies. Salt is random per hash: two
accounts with the same password have different stored strings. Verify is
`subtle.ConstantTimeCompare` over the derived keys, answers `false` with no
error for a wrong password (every wrong password gets the same 401), and a stored
string that does not parse — bcrypt-shaped text, argon2i, a foreign version, a
truncated string, `m=4294967295`, `t=0`, `p=0` — is a false plus an error, never
a panic and never an allocation a database row can ask for.

The store takes the hash and never the password
(`store.UserStore.SetPassword(id, passwordHash)`): this package is the only place
a password becomes a stored string.
