# S7-02 — seal.go: AES-256-GCM secret sealing keyed by SHA-256(NVR_SECRET_KEY)

## Deliverable

Seal(plain, key) / Unseal(sealed, key) with random nonce, base64 stored; key derived from NVR_SECRET_KEY (64-hex), falling back to a derivation from JWT_SECRET so a deployment backs up one secret.

## Exit criteria

- [x] round-trip + tamper detection asserted
- [x] key derivation asserted (same JWT_SECRET -> same key)
- [x] NVR_SECRET_KEY documented as required in production
- [x] no sealed value is ever returned by an endpoint

`docker run --rm -v $PWD/server:/src -w /src golang:1.26 go test ./storage -count=1 -run Seal`

(the card's command; `-run Seal` catches the six `TestSeal*` tests. The whole

held by tests the `-run` pattern does not name.)

## Notes

**Done 2026-11-04.** `server/storage/seal.go` is `Seal`/`Unseal` over
AES-256-GCM. The format is the plan's, pinned by a test:
`base64.StdEncoding(nonce[12] ‖ ciphertext ‖ GCM tag)`, no prefix —
`TestSealedFormatIsThePlansFormat` asserts the decoded length is exactly
`12 + len(plaintext) + 16`, so a format change arrives as a migration and not
as a refactor.

**The key is not derived here.** `config.SealKey()` (S1-04) already answers
"hex-decode `NVR_SECRET_KEY`, else `SHA-256(JWT_SECRET)`", including the rule
that a 64-character value which is *not* hex is an error rather than a silent
fallback. `seal.go` takes the finished `[32]byte`. The derivation criterion is
therefore asserted through the pair: `TestSealKeyComesFromTheConfiguration`
loads the configuration twice and opens one process's row with the other's key.

**Two failures, named apart, because the operator's fix differs.**
`ErrNotSealed` is a stored value this server never wrote — not base64, or too
short to hold a nonce and a tag (a row written by hand, or a column from an
older installation). `ErrSealOpen` is a well-formed value that does not open,
which GCM cannot split into "wrong key" and "tampered", so the honest message
is about the key this process holds. Collapsing the two would send someone
hunting for a lost `NVR_SECRET_KEY` when the fix is to retype one password.
Neither message ever contains the plaintext (`TestSealWrongKeyDoesNotOpen`).

**`Seal("")` is `""`, not a ciphertext of nothing.** "No credential here" has to
stay answerable without the seal key, because `SecretSet()`, the per-kind
validation in S7-10 and the sweeper all ask that question and none of them
should need the key to ask it. `Unseal("")` is `""` for the same reason.

**Deviation from the plan's sketch: `Seal` returns `(string, error)`.** The plan
writes `Seal(plain string, key [32]byte) string`. The nonce comes from
`crypto/rand`, and a sealing path that swallowed that error would write a
credential sealed with a zero nonce — the one mistake that reuses a nonce under
the same key, silently. The error is returned, not logged.

**"No sealed value is ever returned by an endpoint" is enforced at the model,
and asserted here at the model.** The secret columns are `json:"-"` on
`models.StorageBackend` and `models.Webhook`, so an endpoint that serialises
the row cannot echo one; `TestSealedValuesAreNeverSerialised` marshals both
rows and fails if a sealed value, *or the column name*, appears in the bytes.
`SecretSet()` is a **method**, and `encoding/json` does not serialise methods —
so `secret_set` is the API view's job, and the test asserts the model does not
serialise it either, which is what keeps S7-10 from setting it twice. The
response-body half of the criterion is asserted in S7-10 (backends) and S6-07
(webhooks).

**Webhook signing secrets are sealed too.** The plan says the storage columns
are sealed and is silent about `webhooks.secret`; the model comment says only
`json:"-"`. Sealing one and not the other would make "a database backup is
readable" true of half the credentials in it, so S6-06 signs with the unsealed
value and stores it sealed. `docs/configuration.md` now says so, in the section
this card added ("What sealing does, and what losing the key costs") — that is
where the third criterion is met, alongside `.env.example`, which already said
"Required in production".
