## Deviations

1. **The e2e sidecar runs with no go2rtc API auth** (GO2RTC_USERNAME/PASSWORD
   empty, comment in e2e-stack.sh). This is the first time live view was ever
   driven from a real browser, and it found a product-level collision: the
   rendered config protects `/api/ws` with basic auth (config.go:156-158) and
   a browser WebSocket cannot present one — behind credentials, live view is
   unreachable (curl: `401` on `/api/ws`; tile: `unreachable — the media host
   … closed the connection before answering the offer`). Filed as **P-14**
   with the three real options; the e2e stack's no-auth sidecar is honest for
   a 127.0.0.1-bound throwaway and the reason is written in the script.
2. **events.spec seeds through the worker intake** (`POST /api/internal/v1/signals`
   with the worker token, open→extend→close) and flips the seeded camera's
   `record_mode`/`detection_enabled` through the API first: the stack runs no
   detector, signals for a detection-off camera are dropped ("detection
   disabled"), and a clip is cut from segments, which only exist while the
   recorder runs. The explicit `close` builds the clip at close — no post-roll
   wait.
3. **The viewer account is created through `POST /api/users`** — registration
   is 403 by design, so the admin API is the only way one exists. The viewer
   then signs in through the real form; only the non-auth specs inject
   localStorage sessions, and auth.spec is the one that tests the form.
4. **ffmpeg was installed on the host** (`apt-get install -y ffmpeg`, 8.0.1):
   the e2e recorder runs on the host, and the media unit tests had always run
   inside the golang container where ffmpeg exists — the host gap was
   invisible until a spec needed real segments.
5. **Specs are serial** (`workers: 1`): events.spec mutates the seeded camera,
   and live.spec reads it.
