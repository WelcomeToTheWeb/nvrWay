## Notes

**Observed** 2026-11-06 — `cd web && npm run typecheck && npm run test:run`:
`tsc --noEmit` clean, `Test Files 11 passed (11)`, `Tests 157 passed (157)` (the
full transcript is in Verification above). Eight mutations, each reverted, each
failing exactly the test that claims the behaviour (table above).

**The console advises and never refuses.** `server/api/zones.go` states the rule
outright — *"One validator, three readers (console, API, worker)"* — so a fourth
opinion about which polygons are legal is how two installations end up
disagreeing about the same rule. Enter therefore closes whatever is on the board,
**including a two-vertex shape**; the editor says in its own voice that the
server wants 3–32 vertices, and the refusal is the server's 422, with **both**
halves of its body rendered (`zone polygon invalid` + the `detail` that names the
zone). `zoneError`'s own comment is the reason for the second half: *"the
`detail` field is what tells the operator which zone and what about it — 'your
JSON is wrong' is a bug report they cannot act on"*. **Rejected — refusing
locally**: it is the exit criterion's own test made unrunnable (no request, so no
422 to read), and an operator who is blocked before asking never learns the
sentence the API was written to say. `enclosesArea` in `api/cameras.ts` carries
the same rule as a doc line — *"used here to warn, never to refuse"*.

**The canvas is a painting, not the state.** Every vertex lives in React state as
a `0..1` pair and the canvas is repainted *from* it. Not tidiness: a canvas is a
bitmap whose size is whatever CSS gave it, so a rule that lived in canvas
coordinates would be a rule that changes when the window does. The pointer is
normalised the moment it arrives and every pixel after is derived from the stored
number — which is also the only reason the geometry is testable at all. jsdom has
no 2d context, so the suite stubs `getContext` to `null` (what a platform without
one answers) and drives clicks and keys instead; nothing under test needed a
pixel. The rule badge is DOM for the same reasons plus one: it has to be readable
at any density, an operator has to be able to reach it, and its `left: 25%` is
the stored `0.25` read back the other way — the round trip, visible.

**Two write paths, kept apart on purpose.** The row's fields go through
`PUT /api/v1/cameras/:id`, which re-renders go2rtc's config because a row can
change a stream. The polygons go through `PUT /api/v1/cameras/:id/zones`, which
does not, and carries its own audit row with the before and the after. The trap
is that `cameraInput` **also accepts `zones`** — so a form that spread the whole
row into its body would write the rule set through the route that has no zone
ledger and no polygon normalisation, and the audit would say the frame rate
changed. The row form therefore builds its body from a named list of fields and
the test asserts the body has no `zones` key (mutation 7 above).

**The slug is shown and not edited.** It is the name of every stored key the
camera has ever written (`nvr/<slug>/<YYYY>/<MM>/<DD>/…`, S7-07), so renaming one
is a migration, not a text field. **Rejected — offering the field**: the server
allows it, and a console that invites it without moving the footage orphans
recorded days with nothing pointing at them. If v1 grows a rename, it needs the
migration in the same breath, not a smaller input.

**"Saved" is the editor's own memory, not the row's.** The button reads
`saved`/`save zones` against what *this editor* last confirmed with the server.
**Rejected — deriving it from the `camera` prop**: `CamerasPage` passes
`camera={{ ...camera, zones }}`, a fresh object literal on every render of the
row form, so an effect that reset the board on prop change would throw away a
half-drawn polygon on every keystroke in the name box. A save of the row's other
fields refetches the camera and the drawing survives; switching cameras remounts
the editor (`key={camera.id}`), which is where the board is meant to reset.

**Zone ids are minted with a monotone time component, and that is a data-integrity
fix, not a naming taste.** The server requires an id and never mints one, and it
checks duplicates only *within the array it was sent* — so reusing the id of a
zone that was deleted is accepted. Event rows store zone **ids**
(`server/api/events.go` resolves them to names from the camera row on every
read), so a new rule that inherits a dead rule's id silently relabels every event
that already fired under it: the proof surface would lie about which rule fired,
months later, with nothing wrong in any row. `mintZoneId` uses
`Date.now().toString(36)` plus a counter, so an id minted now can never equal one
minted before.

**A viewer is told, not hidden from.** The rule set is on screen, the controls
are absent, and the page says `your role can read zones, not change them` (and
`…cameras…` on the row form). The role floor is the server's — `operator`/`admin`
for the writes — read from the session the login or the SSO profile wrote; the
server stays the authority, and a stale local role costs a refusal, not a
secret.

**No picture is not a blocked editor.** `GET /api/v1/cameras/:id/snapshot`
answers 404 with `no snapshot from <slug>: …` when the camera is not producing
(`ErrStreamRejected`, deliberately not a 5xx). The editor repeats that sentence
over the canvas and adds what it means here — *you can still draw, but you are
drawing without a picture* — and still takes points, because an operator knows
where their driveway is and a blackout is not a reason to stop arming a rule.

**Three files became five.** The card named three paths. `api/cameras.ts` is one
home for the vocabulary the editor and the page both need (the rules, the
classes, the limits, `mintZoneId`, `toNormalized`) so neither invents its own;
`CamerasPage.test.tsx` exists because the page's sharpest contract — the row
write never carries `zones` — is a page-level fact no component test can see.

**Not here:** the delete button (admin-only and destructive; role-gated nav is
S8-09, and a destructive control needs that shell to be honest about who is
looking), the router and nav (S8-09 — this page already reads
`useMatch('/cameras/:id')`, so the shell must mount it at both routes, the same
obligation S8-06 left), and i18n (every string is English inline, as v1 scopes
it).
