# S4-04 — Crash handling: ffmpeg exit -> log + camera.status offline + restart backoff

## Deliverable

ffmpeg exit logs, broadcasts camera.status offline, restarts after 10 s with 60 s max backoff; CSV offset resets; a recovered camera resumes numbering from persisted Generation.

## Exit criteria

- [x] killed process restarts and numbering continues (asserted)
- [x] backoff caps at 60 s and resets on a healthy segment tick
- [x] camera.status producers reflect the truth, not the intent

## Notes

- **The policy arrived with S4-01; this card is the suite that pins it.** The
  restart loop, the `ffmpeg exited (%v); last output: %s (restarting in %s)` log
  line, `cameraOffline`, `nextBackoff` and `run.takeHealthy` were all written when
  `cameraLoop` was, and needed no change. What this card added is the two fakes
  the criteria need: `spawnLog.exitWith` (the child dies **on its own**, on a
  schedule the test sets — `Stop` was the only way a process had ever ended, and a
  terminated child is not a crash) and `sleepRecorder` (a backoff is a *sequence*
  of waits, so the honest assertion records the waits: 10 → 20 → 40 → 60 → 60).
- **`camera.status` is asserted as a sequence, not as the newest entry.** The
  first version waited for `hub.lastCameraStatus(...)` to say offline and failed
  **2 of 5 runs**. With the clock injected, the restart backoff is a clock advance
  rather than a wall-clock wait, so the offline state lasts microseconds of real
  time between the offline broadcast and the next spawn's first segment broadcast —
  a 5 ms poll can miss it forever. The test now walks the append-only
  `fakeHub.cameraStatusLog`: an online announcement whose `producers` is the `-i`
  argument of the process that wrote the segment (the sidecar's stream, **not** the
  row's `source_uri`), followed later by an announcement saying offline with
  `producers: []`. Same property, no race. `lastCameraStatus` is gone; a helper
  that returns one entry invites the assertion that raced.
- **The fake truncates the segment list at spawn, as ffmpeg does.** The crash
  suite's `writeSegments` appended, so every generation's tail re-read every
  earlier line: rows and `camera.status` broadcasts grew with the generation
  count, and the suite cost 2.5–5.7 s instead of 0.9 s. S4-03 pinned the same
  behavior for the tail (`TestSegmentTailResetsOnRestart`); the crash suite now
  matches it.
- **"Healthy" is footage, not a process that started.** `run.markHealthy()` fires
  when a segment row is written, and `takeHealthy()` *consumes* the flag, so the
  backoff resets once per spawn and the next crash starts the climb over at 10 s.
  A camera whose ffmpeg starts and writes nothing keeps climbing to the 60 s
  ceiling, which is the point of a ceiling.
- **Numbering after a crash has two halves, and the suite asserts both** on the
  restarted argv: `-segment_list_entry_prefix porch-2-` (the generation came from
  `recorder_gen_<camera_id>`, persisted before the child started, S4-02) and
  `-segment_start_number 2` (generation 1 wrote 0 and 1, so ffmpeg's own restart
  at 0 would overwrite them). `Segments.MaxSegmentNumber` returns -1 when the
  generation wrote nothing, so a fresh generation starts at 0 — and two
  generations can never collide, because the generation is in the file name.
- **A shutdown is not a crash.** `cameraLoop` returns on `ctx.Err() != nil ||
  r.isClosed()` *before* the offline broadcast and the restart, so the last thing
  a stopping recorder does is not "camera offline" and the second-to-last is not
  "start ffmpeg again" (`TestCrashDuringShutdownDoesNotRestart`).
- **CSV offset reset is S4-03's** (`TestSegmentTailResetsOnRestart`): one tail per
  spawn, starting at offset 0. Named here because this card's deliverable does.
- **Corrected by S4-07 (2026-11-03).** The restarted-argv assertion quoted above
  named `-segment_list_entry_prefix porch-2-`; that flag is gone (ffmpeg prepends
  it to the segment name, so the plan's prefix produced names for files that did
  not exist), so the assertion is now on the output pattern,
  `…/porch-2-%d.mp4`. The same criterion — a forced kill, the generation moving,
  the numbering resuming — is now also run against a process that can really die:
  `TestRealFfmpegForcedKillResumesNumbering` SIGKILLs ffmpeg and reads the rows it
  left behind. The backoff, the log line and the online → offline → online sequence
  are unchanged.
