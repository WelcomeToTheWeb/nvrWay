# S7-08 — uploader.go: claim, upload, exponential retry, failed at 20, requeue, enable flag

## Deliverable

Tick every UPLOADER_TICK_SECONDS; ClaimNextJob (FOR UPDATE SKIP LOCKED on Postgres, SELECT + guarded UPDATE in a tx on sqlite); Put then mark uploaded + remote_key; on failure state pending + NextAttemptAt = now + min(5min*2^attempts, 6h); attempts >= 20 -> failed.

## Exit criteria

- [x] claim -> upload -> uploaded asserted
- [x] failure produces exponential next_attempt_at
- [x] attempts >= 20 lands in failed and is visible on ?state=failed and in storage.queue
- [x] a disabled backend claims nothing; in-flight jobs finish
- [x] the uploader never deletes local files (the sweeper's job)

## Notes

**Done 2026-11-04.** `server/storage/uploader.go` is the queue worker: `Tick`
drains, `Run` ticks, and a job leaves the loop in exactly one of three states —
`uploaded`, `pending` with a next attempt, or `failed`. There is no fourth,
because "we'll know from the log" is how a storage tier that has been broken for
a week gets discovered by the footage that is missing.

**One queue, one worker: the sweeper decides, this executes.** The queue has
three actions and the plan gives the sweeper all three, so the loop claims
whatever is oldest and does it — `upload`, `delete_local`, `delete_remote`.
Splitting the actions across two workers would mean two claims fighting over one
queue: `ClaimNext` has no action filter, and a worker that handed back a job it
did not own would either inflate its attempt count or ping-pong with the other
one every tick. So **"the uploader never deletes local files" is a statement
about the upload path**, and `TestUploaderNeverDeletesTheLocalFile` asserts it
that way: after a successful upload the local file is still there, because the
failure mode being prevented is an uploader that unlinks the source the moment
the copy lands — playback would then depend on the tier being reachable, and a
tier that is down would mean footage that used to play. `TestUploaderRunsTheSweepersDeleteActions`
asserts the other half: the loop does run the sweeper's deletes when they are queued.

**The claim is the enable gate, and the worker does not re-check it.**
`ClaimNext` joins the backend row and refuses a disabled one, so a disabled
backend claims nothing. A worker that checked `enabled` *again* after claiming
would strand a job in `uploading` with the bytes already in flight — the one
state that needs `ReleaseStuck` to recover. `TestInFlightJobFinishesWhenTheBackendIsDisabledMidFlight`
drives exactly that: a tier that disables itself during `Put`, and the job still
reaches `uploaded`; the *next* pass then claims nothing.

**The backoff, as recorded instants rather than durations.** `RetryAt(now, attempts)`
is the plan's `min(5min * 2^attempts, 6h)` as a pure function, and the
end-to-end test asserts the delay written to the row on each of nine consecutive
failures: 10, 20, 40, 80, 160, 320 minutes, then 6 hours for the rest. **The
first retry is 10 minutes and not 5, because `attempts` is the count the claim
put on the row** — the claim that just failed is attempt one, and the exponent
counts attempts already made. The doubling stops at attempt 7 (`retryCapAttempts`)
because 5min × 2⁷ already exceeds the cap, which also keeps a hand-requeued row
with a large attempt count from overflowing the shift. A job that never succeeds
is retried for roughly four and a half days before it lands in `failed`.

**The cap is asserted from both sides.** `MarkRetry` (S1-11's) decides
`pending` vs `failed` at `models.JobMaxAttempts`, so the boundary is tested by
writing the attempt count directly: from 18 recorded attempts the next claim
(19) stays `pending`; from 19 the next claim (20) is `failed`. Visibility is
asserted through the two reads the queue endpoint uses — `ListByState("failed")`
returns the job, and `Counts()` reports `Failed: 1` with a non-empty `LastError`.
`GET /api/storage/queue?state=` itself is S7-10's.

**A failure that can never succeed stops now, not after twenty attempts.**
`errPermanent` marks the three cases where the row and the world disagree: the
local file is gone, the backend row is gone, or the job names an action no worker
implements. Left `pending` they would be retried for four and a half days, and
`pending` is the number an operator watches to tell whether the tier is healthy —
so a permanent failure masquerading as a transient one makes a dead installation
look busy. This needed one store addition, `StorageJobStore.MarkFailed`, because
`MarkRetry` reads the row's attempt count and cannot be told to stop early.

**`Enqueue` no longer clears `remote_key`, and that is what makes the sweeper's
chain work.** The key is a fact about the *object*, not about the current
obligation: once the bytes have reached the tier the object has an address there,
and `delete_local` followed by `delete_remote` is meaningless without it. The
old `ON CONFLICT` assignment reset it on every re-enqueue, so the sweeper's own
`delete_remote` job would have had nothing to delete — the queue would have
said "uploaded, address unknown". `Requeue` (moving to a different backend)
still clears it, because there the address really is invalidated.

**A pass is bounded by count *and* by wall clock, and the time bound is the one
that matters.** `maxJobsPerTick` is 200; `maxTickWork` is 5 seconds. The first
temptation on a tier failure is to end the pass when an error names the tier as
unreachable, on the theory the rest of the queue will fail the same way — but the
queue is one queue across every backend, so the oldest job being unreachable says
nothing about the next one, and a dead bucket would then starve a healthy one to
zero jobs per tick forever. The budget bounds the damage without that lie.

**A backend is opened per job, not cached.** Every driver's constructor is cheap
— minio and gowebdav build a client without dialling, and sftp dials per
operation because `Backend` has no `Close` — so a cache would buy nothing and
would cost a stale credential surviving an edit until restart.

**The date in the key comes from the manifest, never from the file name.** The
uploader could take the slug from the recorder's own name (`<slug>-<generation>-<n>.mp4`)
but it cannot take the *date*, and the plan's clock rule says no time is read
from a file name. So `JobFacts.SegmentFacts` returns the slug and `StartTS` from
the segment and camera rows that already have them, which closes the temptation
rather than warning about it. An event clip or snapshot needs no lookup: the
job's id *is* the event's id.

**`Run`'s `enabled` callback is called from the loop's goroutine, so it must be
safe to call concurrently.** The first `-race` run caught this in the test
itself — a bare `enabled` bool written by the test and read by the loop — and the
contract is now in the doc comment, because the real caller (a settings flag
read from the API's goroutine) makes exactly the same mistake.
