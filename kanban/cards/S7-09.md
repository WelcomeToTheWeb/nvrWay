# S7-09 — sweeper.go: the seven sweeps, with the un-uploaded protection window

## Deliverable

Every 15 min: local segment delete past local_retention_days (keeping uploaded_at IS NULL rows for max(3*local_retention_days, 7 days)), event-referenced segments, event rows past EVENT_RETENTION_DAYS (media first), remote keys past REMOTE_RETENTION_DAYS (0 = forever), webhook_deliveries past 30 d, audit past 365 d, uploaded jobs past 30 d.

## Exit criteria

- [x] un-uploaded footage is never destroyed inside the protection window; force-delete is counted in the log
- [x] remote delete only past REMOTE_RETENTION_DAYS, 0 = keep forever asserted
- [x] one summary log line with the counts, broadcast as storage.queue

## Notes

**Done 2026-11-04.** `server/sweeper/sweeper.go` is the only thing in this
installation that destroys footage, which makes its bugs measurable in lost
recordings rather than in an error the operator can see. It is written as
refusals, and fourteen tests in `./sweeper` hold it to them.

**The seven sweeps, in the plan's order, and the order is not cosmetic.** The
remote sweep clears a row's `remote_key` as it queues the delete, and the local
sweep refuses to delete a row that still has one — so a row whose last copy was
*just* queued for deletion survives one more sweep. `TestARowOutlivesTheSweepThatGaveAwayItsLastCopy`
pins that: pass one queues and keeps, pass two removes. A row deleted in the same
pass that gave away its last copy would orphan the object if the delete job then
failed.

**An eighth duty: `ReleaseStuck`.** The store has had it since S1-11 and nothing
called it. A claim still open a quarter of an hour later belongs to a worker that
died holding it — a pass is bounded by five seconds — and it runs **first**,
before anything looks at the queue.

**The protection window is `max(3 * local_retention_days, 7 days)`, and the
floor is the part that matters.** A 1-day local window would otherwise protect
un-uploaded footage for three days, which is shorter than most outages last.
Three cases in one sweep: uploaded footage past its window goes; un-uploaded
footage 5 days old with a 7-day floor stays; un-uploaded footage 9 days old goes
and lands in `ForceDeleted`, which is an outage report rather than a housekeeping
count. It also gets its own `Warn` line, because a non-zero number there means
footage was destroyed without a copy surviving, and that should be filterable
rather than buried in the summary.

**`REMOTE_RETENTION_DAYS=0` means keep forever, and the sweep says so by doing
nothing.** Not by treating zero as "no window configured" and emptying the tier —
which is the mistake the plan's zero-is-a-real-value rule exists to prevent.
Asserted with a 400-day-old uploaded segment: nothing queued, key intact, row
alive.

**A segment row is deleted only when the footage exists nowhere.** No local file,
no remote key, no live event that can reach the window. While any of the three
remains, the row is the index to it, and an object the database forgot is a bill
nobody can cancel. This is why the report separates `local_deleted` /
`force_deleted` / `event_segments_deleted` (files reclaimed) from
`segment_rows_deleted` (rows forgotten): they part company on purpose. A row
outlives its file whenever the tier still holds the object, and outlives the tier
copy until event retention, because the timeline is allowed to show what was
recorded after the footage aged out.

**Two bugs the sweeper found in code that already shipped.**

1. **`delete_remote`'s key is `Target`, not `RemoteKey`.** The model says so
   ("Target is the local path (upload) or the remote key (delete)"), and both
   handlers that already enqueue purges — S3-03's camera delete, S6-04's event
   delete — fill `Target` with the key and leave `RemoteKey` empty. S7-08's
   worker read only `RemoteKey`, so it would have called every purge those
   handlers queued permanently failed, and the objects would have sat on the tier
   forever with nothing pointing at them. `TestUploaderDeleteRemoteFollowsThePurgeJobsTheAPIAlreadyEnqueues`
   now drives the job exactly as those handlers write it.
2. **An event's two objects need two job ids.** The queue's primary key is the
   object's id, and an event has a clip *and* a snapshot, so the repo's existing
   convention is `<event_id>:clip` and `<event_id>:snapshot`. The key layout
   cannot use that verbatim — `nvr/events/<id>:clip/clip.mp4` is not the plan's
   layout — so `eventIDFromJobID` cuts at the first colon (a UUID has none) and
   the layout stays `nvr/events/<event_id>/clip.mp4` either way.

**Two more the tests caught in the sweeper itself.**

3. **The candidate query has to run at the *shortest* window in the
   installation, not the longest.** Retention is per camera and the store's list
   is per cutoff, so the query asks "what could be eligible anywhere" and each
   row is then checked against its own camera's window. Run at the longest
   window, a camera with a one-day window never appears in the candidate list at
   all, and the per-camera check downstream cannot fix a list that never contained
   the row. `TestPerCameraRetentionBeatsTheInstallationDefault` has a 14-day
   installation and a 1-day camera and asserts both numbers are honoured.
4. **The event-reference check has to come *before* the file is removed.** The
   first version deleted the file and then noticed an event could still rebuild a
   clip from that window, so it protected the row and destroyed the footage —
   which is not protection. Now a referenced segment is skipped entirely: the
   local window does not apply to footage an event is built from, and the event's
   own retention decides in sweep (2).

**"Referenced by an event" is a time question, not a foreign key.** The clip
builder selects segments by range (`ListRange`), so the sweeper asks the same
question — `EventStore.OverlapsWindow` — widened by the clip's roll margins,
because a segment only the pre-roll reaches is still footage that clip is cut
from. When the answer cannot be read, the sweeper **assumes yes**: the one rule
is that it does not destroy what it could not check.

**Sweep (2) is what keeps a `record_mode=events` installation from growing
forever.** The two retention lists in the store are continuous-only, so an
event-triggered camera's segments appear in neither; without this pass their rows
and files would only ever accumulate.

**Sweep (3) purges media before the row, and an event's purge is two jobs.** An
event row is the only thing that names its clip and snapshot keys, so deleting
the row first would leave two objects on the tier with nothing pointing at them.

**Sweep (4) covers event media too, so `REMOTE_RETENTION_DAYS` means the same
thing for a clip as for a segment.** The consequence is worth stating plainly: an
event older than the tier's window is a record of what happened, not something
that plays, and its row says so by carrying no upload stamps.

**One summary line, one message.** `Sweep` logs a single `storage sweep` line
with every count, and broadcasts the same `Report` as `storage.queue` — including
the queue's own counts, so the one message the storage page listens to carries
what the storage page shows. Failures that did not stop the sweep ride along in
`Problems`, because a sweep that quietly skipped half its candidates looks exactly
like a healthy installation with nothing to do.

**Seven store queries added**, all small, all things the sweeper cannot do
without: `Events.OverlapsWindow`, `Events.ListOlderThan` (oldest first — the
timeline's newest-first ordering would leave the oldest events' media unpurged
while their rows were deleted), `Events.DeleteByIDs`, `Events.ClearRemoteMedia`,
`Segments.ListPastRetention` (any kind), `Segments.ListRemoteOlderThan`,
`Segments.ClearRemoteKeys`. The last deliberately clears `remote_key` and **not**
`uploaded_at`: clearing both would send a segment whose local file is still on
disk back into the "an upload outage is protecting this" set, and its local copy
would then be held for three times the retention window it already passed.

**Single-writer rule respected:** the package assumes it owns the media tree. Two
installations sharing one `SEGMENTS_DIR` would double-delete, and two sweepers on
one database would race the retention clock.
