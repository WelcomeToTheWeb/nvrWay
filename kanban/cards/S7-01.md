# S7-01 — storage.go: Backend interface + Open dispatch (+ OpenDefault)

## Deliverable

Put/Get/Stat/Delete/List/Ping over a Backend interface, kind dispatch (s3, webdav, sftp, fs), OpenDefault from the IsDefault row.

## Exit criteria

- [x] Open returns the driver named by the row's Kind
- [x] Ping failure maps to the named errors the API reports (discovery_unreachable, bad credentials, sftp host key changed, bucket missing)
- [x] no driver is linked by a binary that does not use it

## Notes

**Done 2026-11-04.** `server/storage/storage.go` is the plan's interface
verbatim — `ObjectInfo{Key,Size,ModTime,ContentType}` and
`Put/Get/Stat/Delete/List/Ping` — plus `Open`, `OpenWithSettings`,
`OpenDefault`, the four named errors, and `ErrorCode`.

**The four names are the sentinel messages, not a table.**
`ErrUnreachable = errors.New("discovery_unreachable")`, and so on, so the name
a driver wraps *is* the name the operator reads and there is no second place
for it to drift. `ErrorCode(err)` maps by `errors.Is`, so a driver may wrap the
name in whatever sentence the log wants. Two ordering decisions are asserted:

- `ErrHostKeyChanged` is tested **before** `ErrBadCredentials`, because an SFTP
  host-key change is an authentication-shaped refusal and a driver that wrapped
  both must answer the more specific one — "bad credentials" would send someone
  to retype a password when the answer is "someone is standing between you and
  that server".
- A driver that *copies* the name into its own sentence instead of wrapping it
  maps to `""`. That is asserted on purpose: it is the mistake that makes a
  connection test unnameable, and it is invisible until a console shows a
  MinIO stack trace.

**A fifth failure that is deliberately not one of the four: `ErrBadKey`.** A
credential sealed with a key this process does not have (S7-02) is not *bad
credentials* — the credential may be exactly right, and telling an operator to
retype a password when the fix is `NVR_SECRET_KEY` wastes their morning. It
maps to `""` and the API answers its own sentence.

**Which columns are secrets is a property of the kind, not of the row.**
`unseal` opens `access_key`+`secret_key` for s3, `password` for webdav,
`password`+`private_key_path` for sftp, and nothing for `fs`. An `fs` row
carrying a stray password is ignored rather than failed — the operator's local
backend is not broken by a field a form left behind. `Username` is never
sealed: it is in the URL and the console shows it, and sealing it would make
"which account does this backend use" unanswerable from a backup.

**Deviation from the plan's sketch: `Open` takes the seal key.** The plan
writes `Open(ctx, b *models.StorageBackend)`. The row's credentials are sealed
text, so *something* must hold the key, and the alternative — a package-level
key set at boot — is a hidden global in the one package whose whole job is not
leaking secrets. `Open(ctx, row, key)` and
`OpenWithSettings(ctx, row, key, settings)` (the settings store is S7-06's
host-key pin) are the two entry points; `OpenDefault(ctx, st, key)` reads the
`IsDefault` row and passes `st.Settings` through.

**Kind dispatch is a registry, not a switch, and the reason is a criterion.**
Each driver file adds itself with `registerDriver(kind, fn)` in `init()`, so
the package compiles and the dispatch is testable before every driver exists,
and a build that does not compile a driver file does not link that driver's
SDK. A duplicate registration **panics** — two files claiming one kind is a
build in which one driver silently never runs, which is a bug that survives to
a deployment. `RegisteredKinds()` answers in `models.StorageKinds` order, not
map order, because the answer goes in a boot log that has to diff.

**`unseal`'s default branch distinguishes a build error from a test double.** A
*valid* storage kind that has a driver but no credential rule is a kind added
without declaring its secrets — refused, because the alternative is a driver
silently starved of its password and failing at the tier with "bad
credentials". A kind that is not a storage kind at all (the suite's
`test-fake-tier`) gets no credentials and no error.

**`OpenDefault` answers `ErrNoBackend` by name.** An installation with no
storage destination is a state, not a failure — the delete route already says
"no storage tier is configured: nothing remote to purge", and the uploader logs
the same words once per tick rather than pretending the queue is idle. The
store's rule that one enabled backend is the default without being marked
(S1-11) is passed through, and two enabled backends with nothing marked is
*no default* rather than a coin flip.

**"No driver is linked by a binary that does not use it" is asserted on the
dependency set.** `TestNoDriverIsLinkedByABinaryThatDoesNotUseIt` reads
`server/go.mod`, fails on any storage SDK the plan does not name
(`aws-sdk-go`, `ncw/swift`, `jlaffaye/ftp`, `minio-go/v6`, …) and fails if any
of the five pinned modules (`minio-go/v7`, `gowebdav`, `pkg/sftp`,
`x/crypto`, `gofakes3`) has been dropped — which is what stops a driver card
from answering its kind with a stub. The pins themselves are Step 1's
(`server/deps/deps.go`), so this card changed code and not a dependency set.
