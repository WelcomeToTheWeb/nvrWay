## Notes

No bundled IdP in v1; this is the only IdP the tests use.

**Two shapes, one implementation.** `go run ./sso/testidp` needs the directory to be
`package main`, and a Go test suite needs an importable package, so the directory is
the CLI (`testidp.go`, `package main`, the four flags the card names plus the user
the IdP asserts, `-break`, `-require-pkce`, `-no-consent`) and the provider itself
lives in `server/sso/testidp/provider/` (`package provider`, importable as
`nvr/server/sso/testidp/provider`). The CLI and the tests run the same handler code;
`provider.Listen(addr, opts)` is the CLI's path, `provider.New(opts)` the tests'.

**Ported from OurWay, and changed where nvrWay differs.** No SAML half (there is no
SAML). The issuer is a value, not `httptest.Server.URL` — the CLI publishes
`http://localhost:9500` as `iss` and as every endpoint in the discovery document,
which is what an operator types into the provider row. `Options.ClientSecret` is
enforced at the token endpoint (`invalid_client`), because nvrWay's provider row
carries a client secret and a fixture that ignores it proves nothing about it.
`Claims.Username` publishes `preferred_username`, the claim S2-04's `uniqueUsername`
prefers. `JWKSFetches()` counts the GETs, so a test can assert the refresh rule
against the provider as well as against the client.

**A code is spent only by a request that passed every check.** `peekCode` reads the
claims, the PKCE check runs, and `consumeCode` spends it after. OurWay consumed the
code at the top of `/token`, so an attacker holding an intercepted code could burn
the victim's login with a failed attempt.

**Consent is a real screen, and a scriptable URL.** The consent page prints subject,
email, `email_verified`, name and groups — the facts the contract's headline test is
about — and offers approve / approve-as-unverified. `GET /consent?approve=<state>`
is the same step as one URL, which is what makes the card's `curl -b jar -L` walk
possible without a form parser. `/callback` is the fixture's own redirect sink, so
the walk has a `redirect_uri` that answers.

**The fixture is tested against the verifier, not against a copy of the rules**
(12 tests, `provider_test.go`): the discovery document is read by `sso.Discover`
itself and every `-break` shape arrives as the named kind
(`discovery_document`, `issuer_mismatch`, `no_code_flow`, `discovery_unreachable`);
the JWKS is read by `sso.JWKSClient.Probe`; the consent walk's `id_token` verifies
through `sso.JWKSClient.VerifyIDToken` with the login's nonce; the sabotage shapes
(`expired`, `foreign_aud`, `wrong_key`, `none`, `hs256`, `missing`) are refused by
the code under test; `nonce_swap` mints a token that **verifies** and carries the
earlier login's nonce — the shape only the flow's nonce check can refuse, which is
why `nonce_mismatch` exists; PKCE is refused with no verifier, and refused with no
challenge under `-require-pkce`; the client secret is enforced; a code is single
use; rotation keeps logins verifiable while both keys are published, and a **cold**
client refuses the retired key.

**Finding, recorded (2026-11-02):** the PKCE constants the suite uses are computed,
not remembered. The pair written from memory (RFC 7636 appendix B's verifier
`dBjJhvNaTfJmYEUPuDaFHjFDBUC2QnKe9LZDBcQKmvk` with challenge
`E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM`) does **not** match its own S256
transform — `python3 -c "import hashlib,base64; print(base64.urlsafe_b64encode(hashlib.sha256(b'dBjJhvNaTfJmYEUPuDaFHjFDBUC2QnKe9LZDBcQKmvk').digest()).decode().rstrip('='))"`
answers `QRy8Cz78gnbyjv7z_qjaOBueDRH805HXtQO9iDyW3aU`, and the suite failed four
tests with `code_verifier does not match the challenge` before the constants were
computed. The fixture and the CLI now carry the computed pair.

`verify.sh` does not exist in nvrWay yet (Step 9 owns the CI/scripts surface), so
"for verify.sh step 8" is honoured by the CLI + this walk, which is the same thing
that script will run.
