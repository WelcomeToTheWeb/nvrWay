## Notes

**The secret check is on the bytes, not the shape.** Not "the view has no secret
field" but "the bytes of every response do not contain the secret" — list, create,
update, deliveries and delete — which also catches a handler that puts it in an error
message. The suite then reads the column back and asserts it is *sealed* text that
opens with this installation's key, because a route that stored the plaintext would
pass every byte check above.

**An omitted secret and an explicitly empty one are different acts, and the seal
makes the test of "kept" interesting.** The console reads `secret_set` and never the
secret, so every save it performs omits the field; a route that read an omitted secret
as "clear it" would un-sign every endpoint the moment someone renamed it. The flags
come from what the payload sent, not from the row afterwards. And because the seal uses
a fresh nonce, re-sealing the same plaintext produces different bytes — so "kept" is
asserted by opening the column and comparing the plaintext, not the ciphertext.

**A refused write is a ledger row too**, with the reason in its details and outcome
`refused`. The denial by role is already audited by the middleware that answers it, so
the handlers only have to record the refusals they decide themselves. The update row
carries `changes` as `[before, after]` pairs, including `secret: "cleared"` — the next
person's question will be why the receiver started rejecting signatures.

**The route refuses endpoints that would save cleanly and then hear nothing**: no name,
no URL, a URL that is not http/https or has no host, a URL carrying `user:pass`, an
empty `events` list, a trigger this build never sends, and a `camera_id` that names no
camera. Every one of those is a row that looks configured in the Settings page and
never delivers — the failure mode with no symptom on screen. The trigger check is
against `webhooks.TriggerClose` rather than a string in this file, so the surface and
the delivery loop cannot drift apart.

**The history is the answer to "why did my hook fail", and the answer is the
sequence.** The endpoint row's `last_error` is the one-line version; the deliveries
route carries 500 → 500 → 200, which is what tells "it recovered" apart from "it has
never worked". The endpoint comes back inline with the page, because the drawer shows
both and one request that answers both is one the console cannot get out of sync.
`?status=failed` is a filter in the store rather than a computation over the page,
because the successes are not the thing being read.

**The payload travels as a JSON object, not a string inside a string.** The operator's
second question after "why did it fail" is "what did we send it", and a console should
answer that without a second request. The guard for a row that is not valid JSON quotes
it rather than dropping it — a hand-edited database should not hide the thing the
operator came to look at.

**Two pagination details that are easy to get wrong.** The route asks the store for one
row more than it shows so `truncated` is a fact rather than a guess, and the store's own
clamp sits at 500 — above this route's 200 ceiling — precisely so the probe cannot be
the thing that answers "there is nothing more" at the ceiling. The order carries an `id`
tiebreaker: two attempts of one delivery can land in the same millisecond, and an offset
page over a tie the database resolves differently per query skips a row on one page and
repeats it on the next.

**No test-notification route, deliberately**, even though `AuditWebhookTest` is already
declared and the old docs named one. A test delivery lands in the same history the
operator is reading to answer "why did my hook fail", and the payload shape for an
event that never happened is a contract the plan does not settle. The audit constant
stays declared and unused.

**Deviations from the card's `paths`, all in service of the routes.** `store/webhooks.go`
gains `status`/`offset` on `ListForWebhook` (one method rather than a near-duplicate
second one; the six existing call sites moved) and `CountForWebhook` so the delete can
report the history that went with it. `models/json.go` gains `JSONStringListToJSON`, the
writer that pairs with the `JSONStringList` reader every JSON column already uses.
`handlers.go` mounts the surface on the existing `/api` admin group, so the routes are
`/api/settings/webhooks` as the plan words them.
