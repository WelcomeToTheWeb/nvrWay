# P-08 — storage_jobs.id is a uuid column; the purge jobs' "<id>:clip" suffix will not land on Postgres

## Deliverable

A job row is keyed by the object it owes, and one event has **two** media objects —
its clip and its snapshot — so the two jobs cannot share one id. Both call sites
suffix the event id instead: `server/api/cameras.go:618,635` (the camera purge,
S3-03) and `server/api/events.go:651-652` (the event purge, S6-04) enqueue under
`<event_id>:clip` and `<event_id>:snapshot`. `models.StorageJob.ID` is
`gorm:"type:uuid;primaryKey"`, and the baseline schema is AutoMigrate over that
model (`server/store/migrate.go`), so on the deployment target the column is
`uuid` and a suffixed id is not a uuid.

Decide how a job names one object's media on Postgres, state the choice, and put
both call sites behind one helper so they cannot drift. The options, in the order
they were considered:

- **a versioned migration widening `storage_jobs.id` to `text`** — cheapest, and
  the queue's id was never a real uuid; it is a key.
- **a deterministic id derived from (object id, kind)** — e.g. a UUIDv5 of
  `"<event_id>:clip"`, which keeps the column a uuid and the key stable.
- **a uuid surrogate plus a `object_key text unique` column** — the most
  conventional, and the most work: every `GetByID` caller changes.

## Exit criteria

- [x] the choice is written in these Notes, and the reason the other two were
      rejected
- [x] enqueueing a clip job and a snapshot job for one event succeeds against a
      real Postgres (the sqlite suite cannot see this bug — sqlite stores the
      column as text and accepts the suffix)
- [x] both purge call sites go through one helper, and the helper is named in
      `docs/architecture.md`'s queue section
- [x] the store suite covers "one object, two jobs" and asserts both rows
      survive, on the same database the deployment uses

**Observed 2026-11-07 — the dev stack's Postgres:** after migration v2,
`\d storage_jobs` answers `id | text | not null`, and verify.sh gate 7 listed
`nvr/events/6a29b890…/clip.mp4` and `…/snapshot.jpg` on the tier — two suffixed
job rows for one event, enqueued, claimed, uploaded and marked, on the database
the deployment uses. Before the migration the same enqueue answered
`ERROR: invalid input syntax for type uuid: "7b2606b1-…:clip" (SQLSTATE 22P02)`
in the server log and the tier stayed empty.

## The choice (written here as the exit criterion demands)

**Migration v2 widens `storage_jobs.id` from uuid to text** (`store/migrate.go`:
postgres-only `ALTER TABLE storage_jobs ALTER COLUMN id TYPE text`, recorded as
a no-op on sqlite so the ledger has the same shape on every dialect; the model
tag is `type:text` so new installs are born right). The queue's id was never a
uuid — it is the object's key, and an event's two objects are
`<event_id>:clip` / `<event_id>:snapshot`.

Rejected: **UUIDv5 of `"<event_id>:clip"`** — keeps the column a uuid but makes
every debug read (`select … where id = …`) require deriving the hash, and the
uploader already parses the suffix back out to find the event row, so the
suffix would have to live in the value anyway. **A uuid surrogate plus a
`object_key text unique` column** — the most conventional and the most work:
every `GetByID` caller changes (the API's queue view, the requeue route, the
uploader's claim/mark path) to buy nothing the widened key does not already
give.

The one naming helper is `store.EventJobID(eventID, kind)`; all six writers —
the camera purge (2 sites), the event purge (2), the clip builder, the snapshot
writer — call it, and `storage.eventIDFromJobID` is the reader of the same
contract. Named in `docs/architecture.md`'s storage-flow section.

Coverage: `TestEnqueueUploadQueuesToTheDefaultTierOrSkipsIt` (store) enqueues
`ev-1:clip` and reads the row back; `TestUploaderMarksTheSourceRowThatOwnsTheObject`
(storage) settles segment + `<id>:clip` + `<id>:snapshot` in one Tick and
asserts all three source rows carry their marks.

## Notes

Found 2026-11-04 while writing S6-04's delete test, which asserts two queued jobs
per event. The sqlite test target hides it; the claim was checked against a real
Postgres (postgres:16-alpine):

```
$ docker exec pguuid2 psql -U postgres -c "select '9a1855df-5aa0-4b3d-8a34-5ba0dbb0ce0f:clip'::uuid as suffixed"
ERROR:  invalid input syntax for type uuid: "9a1855df-5aa0-4b3d-8a34-5ba0dbb0ce0f:clip"
```

Not fixed inside S6-04: the fix is a schema decision (a migration, or an id
derivation), and S6-04's deliverable is the event surface. The camera purge has
had the same shape since S3-03, so this is one bug with two call sites, not a new
one. It bites the first deployment that runs on Postgres rather than sqlite —
which is every deployment the plan describes, so it is a pre-production card, not
a v2 nicety.
