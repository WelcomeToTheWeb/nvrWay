## Notes

This card's value was not the two tests. It was that they ran: a fake child
accepts any argv it is handed, and the plan's ingest command — pinned token by
token by S4-02 and never executed — was wrong in three places. All three are now
fixed in `FfmpegArgs`/`cameraLoop` and pinned by both a fake and the encoder.

- **`-segment_type mp4` does not exist.** ffmpeg 7.1.5 (Debian trixie, the
  `golang:1.26` base) and 8.1.3 (the build go2rtc ships) both answer
  `Unrecognized option 'segment_type'. Error splitting the argument list` and
  exit 8: **no process, no segments, no recording, forever**. The segment muxer's
  option is `-segment_format`, verified by `ffmpeg -h muxer=segment`. The
  deployment would have run the plan's line against a real ffmpeg and produced
  nothing but a restart backoff.
- **`-segment_list_entry_prefix <slug>-` is prepended, not substituted.** With
  the plan's pattern `<slug>-<n>.mp4` and prefix `<slug>-`, the list ffmpeg
  writes names `porch-1-porch-1-0.mp4` — measured, not inferred:
  `p-1-p-1-7.mp4,0.000000,1.080000`. That resolves to a file that does not
  exist, so every row gets `bytes = 0`, `Segments.MaxSegmentNumber` cannot read
  its own last number back out of the name (so a restart starts ffmpeg at 0 and
  overwrites), and the manifest points at footage that is not there. With **no**
  prefix ffmpeg lists the bare basename (`p-1-7.mp4`) regardless of where the
  list file lives — which is exactly what `recordSegment` resolves against
  `SEGMENTS_DIR`. The flag is gone; `SegmentListPrefix` is gone with it, and the
  fakes that play ffmpeg's side now derive the name from the recorder's own
  output pattern (`segmentName` in `helpers_test.go`) instead of from a flag.
- **The list must be empty before the child exists, and the recorder now makes
  that true.** The tail starts each spawn at offset 0, an invariant S4-03 pinned
  by having the *fake* truncate the list at spawn. Real ffmpeg truncates it too —
  but only when its muxer opens, a beat after the spawn — and the kill test
  caught the gap: generation 2 came back with rows naming `porch-1-0.mp4` and
  `porch-1-1.mp4`, the dead generation's lines re-ingested under the new
  generation with the new spawn's clock. `resetSegmentList` now empties
  `SEGMENTS_DIR/<slug>.csv` in `cameraLoop` before `newProcess` is called, so the
  offset-0 read is true by construction instead of by racing ffmpeg's open.
- **The suite is two tests, and each criterion is asserted, not narrated.**
  `TestRealFfmpegSegmentsMatchTheCSVAndTheDisk` reads ffmpeg's own list back with
  the recorder's own parser (`parseSegmentLine`) and walks the rows against it:
  name, path, `seconds` = end − start, `bytes` > 0 **and** equal to the file's
  size, `kind`, `generation`, and `start_ts`/`end_ts` = the instant that
  generation's ffmpeg was handed the clock ± `realSegmentTolerance` (250 ms — the
  time a fork takes, and small enough that a camera clock, a file-name time, or a
  start time taken from the tail instead of the spawn fails). The list is read
  *before* the rows, because the tail lags it by a tick: a row with no list line
  is footage the recorder invented.
  `TestRealFfmpegForcedKillResumesNumbering` SIGKILLs the child (deliberately not
  the recorder's SIGTERM `Stop`, which lets ffmpeg close the segment and write its
  line — a graceful end is not a crash), then asserts the settings counter moved
  to 2, the new argv's `-segment_start_number` is the dead generation's last
  number + 1, its output pattern is `porch-2-%d.mp4`, the new rows' numbers
  continue rather than restart, generation 1's rows survive, the crash was
  logged, and `camera.status` went online → offline → online — read as a
  transition over the append-only log, per S4-04's finding.
- **The source override is what makes this cheap.** `SetSourceCommand` swaps only
  what ffmpeg *reads*: `testsrc2=size=320x240:rate=25:duration=60` with `-re`, so
  media time and wall clock advance together the way an RTSP feed's do. The
  segment arguments, the naming and the numbering — the parts under test — are the
  recorder's own. Three 1-second segments cost 3.4 s.
- **Two real-ffmpeg facts worth having written down.** A `SEGMENT_SECONDS=1`
  segment is really 1.08 s of media time: ffmpeg cuts at the nearest keyframe
  after the requested length, so with `-c copy` the source's GOP sets the segment
  length, not `segment_time`. And ffmpeg writes each list line when the segment
  closes, one tick behind the file — measured at ~1 s latency, which is why the
  tail's 1 s tick is the right order of magnitude and why the suite reads the
  list before the rows.
- **CI** (the card's original note) still has `apt-get install -y ffmpeg` as the
  way this suite gets its encoder; the image above is just that, pre-baked. S9-09
  wires the job.
