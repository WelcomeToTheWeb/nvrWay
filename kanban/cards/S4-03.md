# S4-03 — Segment discovery: tail the ffmpeg CSV into segment rows on the server clock

## Deliverable

Parse appended CSV lines (filename,start_time,end_time), insert Segment rows with StartTS = procStart + start_time, EndTS = procStart + end_time, Seconds, Bytes from os.Stat, Kind = continuous.

## Exit criteria

- [x] absolute times come from the supervisor's start time — no camera clock, no filename parsing
- [x] the CSV offset is tracked and reset on restart (no re-ingest, no skips)
- [x] rows carry bytes > 0 and match the file on disk

## Notes

What the card's prose left open, and what the code does:

- **`Kind` follows the mode, not the plan's single word.** The plan's Step 4 line
  says `Kind = continuous`; the `Segment` model (S1-03) documents `event` as "a
  segment written inside an event window", and the clip builder selects overlapping
  segments of **any** kind. So `segmentKindFor` writes `continuous` for the always-on
  recorder and `event` for footage recorded inside a window. `TestSegmentKindFollowsTheRecordMode`
  pins both. No footage is excluded by kind anywhere in the pipeline.
- **The tail's offset moves past everything it read, including the unfinished line.**
  The first version advanced the offset by the complete lines only and kept the
  unfinished tail in memory — so the next read re-read those same bytes from disk and
  joined them to the copy it already held. The suite caught it as `1 segment list
  line(s) did not parse` and a segment that never arrived. The rule now: keep the
  partial in memory, advance the offset past every byte the read touched.
- **One tail per spawn, starting at offset 0.** That is the card's "offset resets on
  restart": ffmpeg rewrites (`-segment_list` opens with `w`) the list when it starts,
  so the new run's list contains only the new run's segments.
  `TestSegmentTailResetsOnRestart` truncates the list the way ffmpeg does, and asserts
  2 rows from each of two runs, none re-ingested.
- **A segment ffmpeg listed and the filesystem will not show is a row with `bytes =
  0`, stated** (`TestSegmentRowReportsAFileTheRecorderCannotRead`). The manifest is
  the recorder's record of what it wrote; inventing a size for a file that is not
  there is how footage quietly disappears.
- **Lines that do not parse are counted and reported** (`… segment list line(s) did
  not parse`), because a tail that silently swallows rows is the failure mode of every
  file tail, and the manifest is the only place recorded footage is findable.
- **The suites play ffmpeg's side of the contract** (`spawnLog.afterStart`): the
  segment files, the `filename,start_time,end_time` lines, a half-written line, and a
  list truncated at startup. Card S4-07 runs the same assertions against real ffmpeg.
