## Why

Step 5's detector needs a GPU test target, and the plan makes CUDA a build flag +
overlay, not a v1 requirement. The user added an Nvidia GPU for testing. It is
present and bound to the driver — and **no container can reach it.** Finding out
why was worth an hour of Step 3, because the answer determines whether the CUDA
overlay is testable at all on this box, and it is not a code question.

## What is true here (measured 2026-11-02)

- GPU: `AD106M [GeForce RTX 4070 Max-Q]`, PCI `0000:01:00.0`, bound to driver
  `nvidia` (`/sys/bus/pci/devices/0000:01:00.0/driver → bus/pci/drivers/nvidia`).
- Kernel module: **615.78.08** (`/proc/driver/nvidia/version`), loaded, refcount 3
  (`nvidia_uvm`, `nvidia_modeset`, `nvidia_drm`), with the char majors registered
  in `/proc/devices` (`195 nvidia`, `195 nvidiactl`, `506 nvidia-uvm`, `509
  nvidia-caps`).
- This box is an **unprivileged LXC container on a Proxmox host**:
  `/proc/self/uid_map` is `0 100000 65536`, the kernel is the PVE kernel
  (`7.0.14-26-pve`), `/dev` is a tmpfs owned by the mapped root, and `mknod`
  returns **EPERM** even with the full capability set. Docker runs *inside* the
  container (`Docker Root Dir: /var/lib/docker`, AppArmor profile `docker-default`).
- So the container sees the host's sysfs and kernel, and **no host device nodes**.
  `/dev/nvidia*` does not exist here, and cannot be created from here.
- Userspace was absent (no `nvidia-smi`, no `libcuda.so`, no `libnvidia-ml.so`,
  `nvidia-ctk cdi list` → 0 devices) while the container toolkit *was* installed
  (1.20.1, `nvidia` runtime registered).

## What I did, and the exact limit of it

Installed the userspace side **in the container**, at the version the host module
already runs, with no kernel-module change:

```
curl -o NVIDIA-Linux-x86_64-615.78.08.run \
  https://download.nvidia.com/XFree86/Linux-x86_64/615.78.08/NVIDIA-Linux-x86_64-615.78.08.run
sha256sum: 3e3f6dddc2ee767a08185300af7be3cb286ece76698d2dde3524599782d07ffe
sudo sh NVIDIA-Linux-x86_64-615.78.08.run --silent --no-kernel-module
sudo ldconfig
```

(`/usr/local/src/nvidia/NVIDIA-Linux-x86_64-615.78.08.run` keeps a copy for the
host install. `--no-xchecks` is rejected by this installer; `--silent` is enough
on a headless box. The X/libglvnd warnings are irrelevant to compute.)

Now present and version-matched: `libcuda.so.615.78.08`, `libnvidia-ml.so.615.78.08`,
`nvidia-smi`, `nvidia-modprobe`, `nvidia-ctk`. The apt route would have installed
**615.71.09** (`libnvidia-compute-615`, Ubuntu resolute), which against a
615.78.08 module is the `Driver/library version mismatch` class of failure — so
the repo packages are the wrong tool here, and the version match matters: NVML
now loads and answers `Driver Not Loaded`, i.e. the library is right and the
device is unreachable, not the version wrong.

`nvidia-ctk cdi generate` → `failed to initialize NVML: Driver Not Loaded`,
`Found 0 CDI devices`. That is the correct answer for a container with no device
access, and it is the remaining gap.

## What the host must do (outside this container, so: for the operator)

On the **PVE host**, with the same runfile (the host has the module and, as far as
this container can see, no nodes either):

```
sh NVIDIA-Linux-x86_64-615.78.08.run --silent --no-kernel-module && ldconfig
nvidia-modprobe -u -c=0            # creates /dev/nvidia0, /dev/nvidiactl, /dev/nvidia-uvm
nvidia-smi                          # must print the 4070 before going further
```

Then expose the devices to this container (unprivileged LXC needs both the device
cgroup allow and the bind mounts; `pct restart` after):

```
CT=$(pct list | awk '/piWay/{print $1}')
pct set "$CT" \
  --features nesting=1,keyctl=1 \
  --lxc-args "lxc.cgroup2.devices.allow = c 195:* rwm" \
  --lxc-args "lxc.cgroup2.devices.allow = c 506:* rwm" \
  --lxc-args "lxc.cgroup2.devices.allow = c 509:* rwm" \
  --lxc-args "lxc.mount.entry = /dev/nvidia0 dev/nvidia0 none bind,optional,create=file" \
  --lxc-args "lxc.mount.entry = /dev/nvidiactl dev/nvidiactl none bind,optional,create=file" \
  --lxc-args "lxc.mount.entry = /dev/nvidia-uvm dev/nvidia-uvm none bind,optional,create=file" \
  --lxc-args "lxc.mount.entry = /dev/nvidia-uvm-tools dev/nvidia-uvm-tools none bind,optional,create=file" \
  --lxc-args "lxc.mount.entry = /dev/nvidia-modeset dev/nvidia-modeset none bind,optional,create=file" \
  --lxc-args "lxc.mount.entry = /dev/nvidia-caps dev/nvidia-caps none bind,create=dir,optional"
pct restart "$CT"
```

In the container afterwards, in this order, each one proving the layer above it:

```
nvidia-smi                                   # host nodes + container userspace
sudo nvidia-ctk cdi generate --output=/etc/cdi/nvidia.yaml
sudo nvidia-ctk cdi list                     # expect 1 CDI device
docker run --rm --gpus all ubuntu:24.04 sh -c 'ls /dev/nvidia*; ldconfig -p | grep -c libcuda'
```

## What closed it

**`modprobe nvidia-uvm` on the host.** The node was handed
over (`/dev/nvidia-uvm`, `c 506:0`) and CDI was regenerated with it, and CUDA
**still** fails — `cudaSetDevice` → `CUDA failure 999: unknown error ; GPU=-1`,
`cudaGetDeviceCount rc=999 count=0` — because the node has no driver behind it:

```
$ python3 -c "import os; os.open('/dev/nvidia-uvm', os.O_RDWR)"
OSError 6 No such device or address          # ENXIO
$ ls /sys/module/nvidia_uvm                  # absent
$ lsmod | grep uvm                           # nothing
$ lsmod | grep '^nvidia '
nvidia  17186816  1 nvidia_modeset           # main module 615.78.08, UVM absent
```

`mknod` makes the file; only `modprobe` puts the module behind it. Every NVML
check passes in this state — `nvidia-smi`, CDI, `--gpus all`, a container that
sees four nodes — and CUDA is the only thing that notices. That is why
`scripts/gpu-probe.sh` now opens each node and reports the errno instead of
trusting `ls`: it is the trap, and it looks healthy.

Host fix (this container has no `CAP_SYS_MODULE` and no module tree for the PVE
kernel — `modprobe` here fails with "Module nvidia-uvm not found in directory
/lib/modules/7.0.14-26-pve"): `modprobe nvidia-uvm` on the host, from the same
615.78.08 install. `scripts/gpu-probe.sh --cuda` is the closing test, and it is
what closed the card.

My forecast was wrong in one specific way, and it is worth keeping: I predicted
`find /lib/modules/7.0.14-26-pve -name 'nvidia*uv*'` would return nothing (a
runfile install building modules only for the kernel whose headers it found). It
returned **`/lib/modules/7.0.14-26-pve/updates/dkms/nvidia-uvm.ko`** — the module
was built and installed for the PVE kernel all along, in the dkms tree. The gap
was a load, not a build.

CPU-path work (S5-06's CPU provider) is unblocked now and was never blocked by
this; the CUDA overlay (S5-07) is what is waiting.

## Notes

**Observed** 2026-11-02: `nvidia-smi` → "couldn't communicate with the NVIDIA
driver"; `nvidia-ctk cdi generate` → `failed to initialize NVML: Driver Not
Loaded`, `Found 0 CDI devices`; `mknod /dev/nvidia0 c 195 0` → `Operation not
permitted`; `/proc/self/uid_map` → `0 100000 65536`.

Two things this card exists to stop: reaching for `apt install
libnvidia-compute-615` on a box whose module is 615.78.08 (version mismatch, and
the repo has no 615.78.08), and reaching for `--gpus all` in an unprivileged LXC
guest and reading the NVML error as a Docker problem. It is a device-access
problem, and the last criterion above is the operator's to close.

**So: visible, not usable for compute.** The plan's pinned detector stack
(`onnxruntime==1.31.1`) in a `nvidia/cuda:13.1.0-runtime-ubuntu24.04` container
with `nvidia-cudnn-cu13` answers:

```
CUDA failure 999: unknown error ; GPU=-1 ; expr=cudaSetDevice(info_.device_id)
Falling back to ['CPUExecutionProvider']
```

Two version facts fell out of that test, both of them the plan's business:

- **onnxruntime 1.31.1 needs CUDA 13.x and cuDNN 9.x.** Feeding it the CUDA 12
  wheels (`nvidia-cublas-cu12`, `nvidia-cudnn-cu12`) fails to even load the
  provider: `libcublasLt.so.13: cannot open shared object file`. This box's
  driver reports `CUDA UMD Version: 13.4`, so the pin is right and CUDA 12 is
  the dead end — a CUDA-12-built detector image will not run here.
- The CUDA 13 pieces do not all come from PyPI: `nvidia-cudnn-cu13` is a real
  wheel (9.27.0.42), while `nvidia-cublas-cu13` and `nvidia-cuda-runtime-cu13`
  are `0.0.1` sdists that fail to build. `libcudart.so.13` / `libcublasLt.so.13`
  come from the CUDA image (`nvidia/cuda:13.x-runtime`) or apt, not pip. The
  detector's GPU overlay has to say that.
