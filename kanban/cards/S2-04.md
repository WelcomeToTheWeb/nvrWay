## Notes

The failure strings are the console's states; do not rename them.

Ported:

- **`discovery.go`** — verbatim port (comments say nvrWay). The five kind strings
  (`ok`, `discovery_unreachable`, `discovery_document`, `issuer_mismatch`,
  `no_code_flow`) and the four sentinels are asserted by name, one test per
  failure shape: no listener, 503, HTML-instead-of-JSON, each missing endpoint, a
  relative endpoint, an issuer that is not the configured one, a document with no
  `code` flow. A trailing slash on the issuer is the same issuer; an explicit
  discovery URL wins over issuer + well-known.
- **`jwks.go`** — verbatim port plus one deliberate strengthening, below.
- **`contract.go`** — `domainAllowed`, `parseRoleMapping`, `mappingOwnsRoles`
  ported; the refusal vocabulary extended with the card's five named reasons
  (`subject_missing`, `email_unverified`, `domain_not_allowed`,
  `id_token_userinfo_disagreement`, `provider_disabled`) beside the contract's
  existing `no_email_claim` / `identity_pending` / `account_pending` and the flow
  failures OurWay names (`code_exchange_failed`, `nonce_mismatch`, …). A test
  asserts each string exactly and that no two refusals share a string: a shared
  string is one console state standing for two different fixes on the IdP side.
  `IdentityError` carries reason + subject + email + target account, because the
  audit question is "who tried to arrive as whom".
- **`oauth.go`** (this commit) — the code flow. `NewCodeVerifier` /
  `CodeChallenge` (S256, never `plain`), `AuthorizeURL` carrying
  `state` + `nonce` + `code_challenge` + `code_challenge_method=S256`,
  `ExchangeCode` presenting the `code_verifier`, `GetUserInfo` reading the
  **mapped** group claim out of the body as published, and `HandleCallback` in the
  card's order: code → **verify the id_token against the published keys** →
  require userinfo and the signed token to name the same subject → contract gate →
  resolve account → session tokens. `HandleCallback` refuses a **disabled**
  provider before any request leaves; an assertion with **no `sub`**
  (`subject_missing`); a provider that publishes a `jwks_uri` and returns no
  `id_token` (`missing_id_token`); a token signed by an unpublished key
  (`id_token_verification_failed`); a replayed `nonce` (`nonce_mismatch`); the two
  identity sources disagreeing (`id_token_userinfo_disagreement`, naming the
  subject and email the assertion aimed at). JIT provisioning creates the account
  at the **viewer floor** with no password, `uniqueUsername` walking
  `ops` → `ops-2` → `ops-3` so a taken name never overwrites an account, and the
  role mapping owning role assignment on every login (the technician who leaves
  `rmm-admins` stops being admin; roles the mapping never named are untouched).
  The raw `id_token` is never stored — only the claim summary as JSON.

**Deviations from the port, recorded.**

1. **`AuthorizeURL` takes five arguments** (`provider, redirectURI, state, nonce,
   codeChallenge`). OurWay's has four, because nonce was added to the flow after
   its redirect helper was written; the card's own exit criterion is nonce
   binding, so nvrWay carries the nonce at the redirect.
2. **Pending identities are `models.PendingIdentity` rows**, not OurWay's
   pending-`User` rows: nvrWay's `User` has no `PendingLinkUserID`, and S1-12
   built the registry with the separate gate. `resolveAccount` parks the
   assertion (provider, subject, email, claims JSON, `MatchedUserID`) and refuses
   with `identity_pending`, naming the target account and the row an admin has to
   decide. S2-06 owns the approval endpoints.
3. **No SAML, and no per-vendor claim fixups.** OurWay's `IssueSAMLIdentity` is
   not here (no SAML file is copied, `SSOProvider.Type` is fixed to `oidc`), and
   neither is its `switch provider.Type { case "google", "microsoft" }` block:
   an IdP whose claims are named oddly is configured with the claim-mapping
   columns (`ClaimsEmail`/`ClaimsUsername`/`ClaimsName`/`ClaimsGroups`), not
   coded for by vendor name.
4. **The state record is not in this file.** `state_mismatch` / `state_expired`
   are in the vocabulary, and the single-use state record that fills them belongs
   to the SSO endpoints (S2-11); a login handler that stores state needs the
   session store's secret and the API layer that mints the redirect.
5. **`subject_missing` is enforced twice**, at the flow and at the store:
   `FindByProvider` refuses an empty half of the JIT lookup (the P-03 fix in S1-07),
   and `HandleCallback` refuses an assertion with no `sub` before the contract
   gate runs. A test asserts both.

**Deviation from the port, recorded (from the first session, kept).** The comment
in `jwks.go` promises "an unknown `kid` triggers a single refresh; a second miss
for the same `kid` is refused", but OurWay's code refreshes on *every*
verification with an unknown kid — a login loop against an IdP that does not
publish the key the token names costs one extra fetch per attempt, not one.
nvrWay keeps the promise: `JWKSClient` remembers the kid ids it searched for
(`misses`), refuses a repeat miss on the spot, and clears the memory when the kid
turns up. The test counts the GETs: 1 warm fetch, +1 for a rotation to a newly
published `k2`, +1 for the first ghost `kid`, and 0 for five repeats.

No SAML: `saml.go`, `saml_test.go`, `testsaml/`, `capture_vendor_saml_test.go`
were not copied, and `models.SSOProvider` has no SAML column set.
