## What the gate found (this is what it was for)

The nine gates did not pass on first contact — they exposed four shipped-code
gaps, each fixed with a pinned test:

1. **The uploader and the sweeper were never started.** `storage.NewUploader`
   and `sweeper.New` had zero callers in `main.go`, and nothing in production
   ever enqueued an upload job: the queue was empty in the field for a reason
   no suite could see (each suite seeded its own queue). Fixed: `Store.EnqueueUpload`
   + call sites in the recorder (`recordSegment`), clip builder (assemble) and
   snapshot writer (`writeEventSnapshot`); uploader + sweeper wired into
   `main.go` with boot log lines; `SourceRows` marks the segment/event rows on
   upload so the sweeper's un-uploaded protection reads real marks.
2. **P-08 arrived exactly as the card predicted**: `storage_jobs.id` was a uuid
   column and `<event_id>:clip` is not a uuid — Postgres rejected every clip
   and snapshot job (`invalid input syntax for type uuid`) while sqlite smiled.
   Fixed by migration v2 (uuid → text on postgres, recorded no-op on sqlite) +
   the model tag + `store.EventJobID` as the one naming helper for all six
   call sites. See card P-08.
3. **The recorder stranded a camera forever.** When an events window closed,
   the tail stopped ffmpeg and the supervisor exited silently — correct — but
   the run entry stayed in `r.runs`, and reconcile skips cameras that already
   have a run. The next signal reopened the window before any poll could clean
   the entry, so every later pass saw "already running" for a loop that owned
   nothing: recording dead while the tile stayed green (goroutine dump proved
   the cameraLoop was gone). Fixed: the loop deletes its own map entry on the
   way out (identity-checked).
4. **A stalled RTSP input was silent forever.** go2rtc's exec producer died
   mid-stream; the recorder's ffmpeg blocked on read with no timeout. Fixed in
   two layers: `-timeout 10000000` on the RTSP input (verified by SIGSTOP-ing
   the producer: ffmpeg exits "Operation timed out" in ~10 s and the supervisor
   restarts it — gen 29 → 30, segments resumed), and the tail's stall watchdog
   (no segment for 3×SEGMENT_SECONDS+10 s with the child alive → logged stop +
   restart) for a child that hangs without exiting.

## Deviations from the plan's gate wording (each forced by observation)

- Gate 3: "producers containing `exec:` and `ffmpeg:`" — there is ONE producer,
  an `exec:` producer whose binary is ffmpeg; the assertion is
  `"exec:" in prods and "ffmpeg" in prods`.
- Gate 6: "count strictly increasing" — the list is ascending and capped at
  `limit=200`, so a busy camera's count can never rise; the gate queries a
  `from`/`to` window and asserts the NEWEST row's start_ts strictly rises.
  Span tolerance is 2-of-3 of the last rows: a generation-boundary segment is
  cut short by the ffmpeg kill at window close, and that row must not fail the
  gate for the recorder working correctly.
- Gate 7: the plan's `find /var/lib/nvr/remote -name clip.mp4` is a filesystem
  read; this card's own exit criterion says every gate over HTTP, so the tier
  is listed through `POST /:id/prefixes?prefix=nvr/events/<id>/` (polled until
  the clip's upload tick lands).
- Gate 9's listener is an inline python3 ThreadingHTTPServer on 0.0.0.0:9501
  (the container reaches the host through the bridge gateway 172.19.0.1); the
  endpoint is registered fresh each run (a previous run's endpoint would sign
  with the old secret).
- Gate 9's signing secret is STABLE across runs (a file in /tmp), not per-run.
  A run found why: an event already open when the script starts closes on its
  own schedule, and that close raced the endpoint recreation by two seconds —
  the deliverer had read the webhook rows before the delete, so the delivery
  went out under the previous run's row and verified under no secret the new
  run knew. The product was right (rows are read at close time; the ladder
  retried the new row at +0/+8/+58 s exactly as S7-10 specifies); the harness
  was wrong to assume the secret rotates atomically with the row. With a
  stable secret whichever row signs, the HMAC recomputes, and the gate still
  fails a wrong-body or wrong-secret delivery.
