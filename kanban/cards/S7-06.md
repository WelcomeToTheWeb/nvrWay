# S7-06 — sftp.go: password/key auth + host-key pinning

## Notes

**Done 2026-11-04.** `server/storage/sftp.go` is the `sftp` driver: x/crypto/ssh
plus pkg/sftp, password or private-key auth, the host key pinned per backend,
and every path under `RootPath`. 20 tests (35 with subtests) in
./storage -run SFTP; whole suite, `go vet ./...`, `-race` and `-count=2` green.

**The in-test server is the protocol, and its host key can be swapped.**
`ssh.NewServerConn` with `pkg/sftp`'s own `sftp.NewServer` over a temp directory
on the real filesystem, so the driver's client, its transport, x/crypto's
host-key negotiation and pkg/sftp's packet layer all run. The key is presented
from a **fresh `ssh.ServerConfig` built per connection**, which is what makes
swapping it race-free — the library reads `config.HostKeys` during the handshake
and would be reading a field another goroutine is writing otherwise.

**One trap in that setup is worth naming:** `ssh.DiscardRequests` answers every
channel request with `req.Reply(false, nil)` (`connection.go:86`), which refuses
the `subsystem sftp` request, so the client hangs waiting for a subsystem that
was denied. The test server replies `true` to `subsystem` itself.

**The pin is the point, and it is asserted as an interception.** Same address,
same port, same backend row, same working credentials, different key: `Ping`
answers `sftp host key changed`, and so do `Get` and `Put` — every operation
dials, so every operation refuses. The failure names **both** fingerprints (the
pinned one and the presented one), because an operator deciding between "my NAS
reinstalled itself" and "someone is between me and my NAS" needs to see what
changed. The password is not in the message: the credential is still correct,
and sending the operator to the password field would hide the real problem.

**No unsigned host key is ever accepted, stated the other way round.** The only
key a connection trusts is one it has already recorded. A backend pinned to
server A, its row then pointed at server B with different keys and the same
credentials, is refused rather than quietly re-trusted. There is no
`HostKeyFallback` and no `InsecureIgnoreHostKey` in the file. First use pins
(trust-on-first-use, the plan's rule), and the pin is written **before** the
connection is used for anything, so a crash mid-transfer does not leave the next
boot with no pin and a second chance to trust a stranger.

**The pin key is `sftp_hostkey_<backend id>`, keyed by id and not by name** — a
rename in the Settings page must not silently re-trust a key the operator had
already pinned. `TestSFTPHostKeyIsPinnedOnFirstUse` asserts the stored value
equals `ssh.FingerprintSHA256` of the key the server presented, and that a second
Ping neither rewrites it nor fails: the pin is a check, not a nonce.

**`ErrNoPinStore` is a new name, and deliberately not one of the four.** An
sftp backend opened without a settings store cannot pin anything. The server is
fine and the credential is fine, so `bad credentials` would lie; the caller that
hits it used `Open` where `OpenWithSettings`/`OpenDefault` supply the store. A
row with no `ID` is refused for the same reason — no id, no pin.

**The connection is dialled per operation and closed at the end of it.**
`Backend` has no `Close`, and `Open` runs on every upload tick and every playback
request, so a connection memoised on the backend would be one leaked SSH session
per tick. `Get` hands its connection to the returned reader — the only place it
can go, since the caller already has to close that — and `Close` there is
idempotent, because a handler that closes the reader and defers a second close
should not turn a finished 200 into an error. `List` is the exception: **one**
connection serves the whole recursive walk, because a tree four levels deep is
one handshake and five reads, not five handshakes. The cost of the per-operation
rule is a handshake per operation, which on a LAN is tens of milliseconds
against a transfer that moves a video segment.

**`Put` writes `<key>.part` and renames, as the fs backend does.** An sftp server
answers a GET for a file that is still being written, so without the rename the
playback proxy serves a truncated mp4 as a finished one. `List` skips `.part`
names for the same reason, and `TestSFTPPutLeavesNoPartFileAndListSkipsOne`
asserts both: a successful Put leaves none behind, and a hand-planted `.part` is
not listed.

**A second delete reports `ErrNotFound`, like fs and unlike s3/WebDAV.** This is
a filesystem, and a filesystem says "not there". pkg/sftp's `normaliseError`
maps `sshFxNoSuchFile` to the stdlib `os.ErrNotExist`, so the driver checks that
and nothing SFTP-specific — no `ErrSSHFx*` comparison, and x/crypto has no
`ErrPathNotFound` at all.

**Authentication failure has no sentinel in x/crypto, so it is matched by its
sentence.** `client_auth.go` returns
`"ssh: unable to authenticate, attempted methods %v, no supported methods remain"`
and there is no exported error to `errors.Is`. `isSSHAuthFailure` matches that
message and the per-method refusals, and keeps the sentence in the failure. The
host-key check is unambiguous by contrast: x/crypto wraps the callback's error
(`ssh: handshake failed: %w`), so `errors.Is(err, ErrHostKeyChanged)` finds it —
and it runs **before** authentication, which is why a key change is reported even
when the credentials would have worked.

**`RootPath` is this kind's container.** Empty → `bucket missing` at Open (the
same answer fs gives for an empty `root_path`); a path that is not there, or is
a file rather than a directory, → `bucket missing` at Ping; a **relative**
`root_path` is refused at Open, because it resolves against the server's idea of
the user's home directory, which this process cannot reason about and the
confinement check cannot bound. Keys with `..` are refused before the wire, and
`TestSFTPKeyCannotEscapeRootPath` also walks the served directory and fails if
anything landed outside `root_path` — the refusal is checked on the server's
filesystem, not only in the return value.

**The endpoint is a host, and it becomes a dialable address.** A scheme is
decoration (`sftp://`, `ssh://`), a missing port is 22, a trailing slash is
decoration, and an unbracketed IPv6 address gets brackets before the port is
appended. A path in the endpoint is refused: the directory belongs in
`root_path`, and putting it in both fields is the mistake the webdav driver
refuses for its own reason.

**Private-key failures name the path and never the key material.** A missing
file, an unparseable file, and an encrypted file are three different messages;
the third says the key is encrypted and v1 has no passphrase field, detected
with `errors.As(&ssh.PassphraseMissingError)` — the exported name is a *type*,
not the sentinel `ssh.PassphraseMissing` the older docs name. The path may appear
in the message (it is unsealed by the time it is read); the PEM and the
passphrase never do.
