# S3-05 — Apply go2rtc config on every camera write + at boot

## Deliverable

One write path: every create/update/delete re-renders the YAML and calls ApplyConfig, so config cannot drift from rows; boot applies it after a Streams probe.

## Exit criteria

- [x] create/update/delete each call ApplyConfig exactly once (counted in the fake go2rtc)
- [x] boot applies config after probing go2rtc, and a go2rtc outage at boot is logged, not fatal
- [x] no other code path writes go2rtc's config

## Notes

**Observed** 2026-11-02: `go test ./api -count=1 -run Apply` → `ok  	nvr/server/api	0.429s`.

- `Handlers.ApplyCameraConfig` is the writer, and `Handlers.BootstrapGo2rtc` is the
  boot step over the same handler set — `newRouter` returns the handlers now, and
  `main.go` calls the boot step and logs its report.
- A boot outage is a WARNING line naming the peer and the streams and rows it saw,
  and the server boots fully: rows, camera list and console surface keep working,
  and the snapshot answers a named 502. A server that refuses to start when go2rtc
  is down takes the API and the rows down with it and leaves no way to see which of
  the two is broken — and "the compose stack started go2rtc late" is the ordinary
  case.
- The single-writer rule is asserted **against the source**: the suite walks the
  module and requires `ApplyConfig(` to appear in exactly `go2rtc/client.go` and
  `api/cameras.go`, and the literal `"/api/config"` in the client alone. A second
  writer added in a later step looks reasonable in review and is invisible to a
  behaviour test.
- A zone write is asserted to send **zero** config writes (rules are not streams),
  and a refused camera write is asserted to send zero.

## Live-sidecar verification (2026-11-02, go2rtc 1.9.15)

The card's own Note flagged this as the unverified assumption. It is now verified,
and it is false as written.

Observed against a real sidecar (`alexxit/go2rtc:latest`, config mounted at
`/config/go2rtc.yaml`):

- `POST /api/config` with rendered bytes → **HTTP 200**, the file on disk rewritten
  (header comment and all), validation applied.
- The new streams (`porch`, `garden`, `porch_det`) were **not in `GET /api/streams`**
  — not after 3 s, not after 10 s. The live map kept the streams that existed at
  boot, and kept running them from their **old** sources after a config rewrite
  that replaced those sources.
- `PUT /api/streams?name=…&src=…` → 200, written to the file, **stream not started**.
- No endpoint starts a stream at runtime: `api/frame`, `api/frame.jpeg`,
  `api/stream.mp4`, `api/stream.mjpeg`, `api/ffmpeg/<name>` all 404 for a
  config-only stream; `go2rtc -help` exposes no reload switch; the sidecar does not
  watch the file.
- `docker restart` → `GET /api/streams` answers exactly the streams in the file the
  server wrote, producers live. That is the mechanism.

So the write contract holds for **durability** (the file is the boot-time config,
the renderer is its only author, and a write repairs a boot that applied nothing),
and the plan's "the write is visible in `GET /api/streams` within 10 seconds"
requires the sidecar to be restarted after the write. The code comments that
claimed a live re-apply have been corrected to the verified behaviour.

**Open decision (blocking the live half of this criterion):** who restarts the
sidecar, and how. Options as I see them — (1) the server shells out
`docker compose up -d --no-deps --force-recreate go2rtc` after a camera write,
which needs the deploy socket this plan deliberately keeps off the app user
(§4.4), and drops in-flight consumers (Live view reconnects); (2) the supervisor
restarts the sidecar on the server's request over a narrow, dedicated channel;
(3) the manager owns go2rtc as a supervised child of the server and restarts it
directly. The delete path (S4-04) needs the same mechanism, so this is cheapest
to settle now.
