**Admin-only is measured, not asserted.** Every write on the surface — read, create,
role list, role change, delete — is asked with a `viewer` token and an `operator`
token: 10 requests, 10 `403 {"error":"insufficient role"}`, and 10 ledger rows under
the verbs they refused. That is the point of the registry: an operator filtering
`user.delete` sees the attempts, not just the deletions.

**The last admin cannot be removed, demoted, or parked.** All three are the same
installation with nobody who can grant a role, approve an identity, or fix a provider
row, so all three are `409` naming what is at stake:

> this is the last admin account: an installation with no admin has no way to grant a
> role, approve an identity, or fix its provider rows

`lastAdminRefusal` reads `CountAdmins()` at the moment of the write, and refuses when
the count is **unreadable** — an API that guessed here would delete the last admin on
a database hiccup. The rule is about the last admin, not admins: with a second admin
the delete succeeds (tested), and `PUT` to `status: "pending"` is refused on the last
admin because a pending account has no roles and no login.

**Role writes end the sessions they change.** `POST /api/users/:id/roles` closes the
account's live sessions and bumps its token generation, asserted on both paths: the
access token stops reaching the admin surface, and the **refresh** token stops
rotating. The gate already reads the role rows, so a demotion takes effect on the
account's next request — the revocation is what makes it take effect on the session
that is already open, because a live refresh token mints access tokens. The ledger row
carries `from`, `to`, `live_sessions_dropped`, the account as target and the admin as
actor.

**Role-mapping ownership (`422`).** `PUT /api/settings/oidc/:provider/role-mapping`
refuses a mapping that names **`viewer`**, in a message that says why: a mapping
replaces roles on *every* login, so a mapping that owns the floor decides that anyone
in no mapped group has no roles at all — and the person who has to undo it is the
admin that mapping just locked out, through the only door that provider's users have.
A role that does not exist is refused **by name** (`no such role: operators-squad`):
a mapping saved with a typo grants nothing and looks configured. An empty mapping is
allowed — no mapping is the floor standing, not everyone becoming an admin. The
refusal is a ledger row under `oidc.update` with `outcome: refused`.

**A password is never writable on a provider account, from either side.** The account
owner's `PUT /api/auth/password` refuses it (S2-06) and the admin's
`PUT /api/users/:id {"password":…}` refuses it with the same 403 — an admin building
the second door is the same act as the owner building it, and the person who
configured the IdP is the one who must decide how that account gets in.

**Secrets and doors.** No response on this surface carries a password hash
(`models.User` marks the field `json:"-"`, and the tests assert the serialised list
and detail bodies contain no `password_hash` and no password). `GET /api/users/:id`
answers `password_login` as a boolean, which is the fact an operator needs about the
break-glass account, and the live sessions with `source_ip` and `user_agent` — how a
person picks one out of a list. `?token=` is refused on every route here (401, and no
ledger row written): these are the URLs that get pasted into a chat.

**`PUT /api/users/:id` answers what the write ended**, not just what it changed:
`{"user":{…},"live_sessions_dropped":N,"sign_in_required":bool}`. "Did that take
effect?" is the question the admin is asking, and a name-only change says `0`.
