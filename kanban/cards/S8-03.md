# S8-03 — LoginPage + AuthCallbackPage: status-driven buttons and the fragment handoff

## Deliverable

Login renders GET /api/auth/status (local form and/or 'Login with <issuer>'); callback reads #access_token/#refresh_token, stores, routes.

## Exit criteria

- [x] a deployment with no local admin shows no local form
- [x] the callback parses the fragment and routes to /live
- [x] a failed exchange shows a named state, not a spinner

`npm run typecheck` and `npm run build` exit 0. Tests were written first and run red — `Failed to resolve import "./LoginPage"` / `"./AuthCallbackPage"` — with the 23 existing tests still green.

**The contract was read from the server, not assumed.** `GET /api/auth/status` answers `{local_login, oidc:[{provider,name,issuer}], registration:false}` where `local_login` is `Users.CountLocalLogin() > 0` (api/auth.go `AuthStatus`). The SSO handoff is a **fragment** both ways (api/sso_routes.go): success `#access_token=…&refresh_token=…`; refusal `#error=<reason>&provider=<name>&error_description=<detail>`, plus `&pending_identity=<id>` for an `IdentityError`. The 13 reason literals were enumerated from `server/sso/` and each is rendered as its own sentence — a pending identity, a disallowed domain, and an IdP asserting two subjects in one login are three screens with three fixes.

**Deviation — the button names the provider, not the issuer.** The plan says `Login with <issuer>`. `issuer` is a URL (`https://id.example.com`); `name` is what the operator called the provider when they added it. The button reads "Sign in with Okta Work" and the issuer is rendered as secondary text beneath it, so the plan's intent survives — the issuer is the one fact that tells two similarly-named providers apart, and it is on screen.

**The authorize link is an `<a href>`, not a fetch.** `GET /api/auth/sso/:provider/authorize` (api/sso_routes.go:172) hands the browser to the IdP and back; that redirect chain cannot happen inside an XHR. Asserted as `href === '/api/auth/sso/okta/authorize'`.

**Beyond the card, because the card did not say it: the callback scrubs the fragment.** A token left in the address bar is a token in the browser history, on the screen, and in anything that reads a URL. `history.replaceState` runs before adoption, and a test asserts `window.location.hash === ''` after the handoff.

**Beyond the card: a half handoff is its own state.** `access_token` without `refresh_token` is *not* adopted — it would die at the 30-minute mark with nothing to renew with (the rotation rule from S8-02). The page says so and offers the door again.

**Beyond the card: the raw reason code is printed beside the sentence.** A reason this page cannot interpret is still a fact the operator can quote. `id_token_userinfo_disagreement` appears verbatim on screen even though it has a sentence of its own.

**A StrictMode guard the card does not mention, and the test that had to be rewritten to justify it.** React 18 StrictMode mounts, unmounts and remounts the effect on the same instance — probed here: 2 effect runs under `StrictMode`, 1 without. The first pass scrubs the fragment, so a second pass reads an empty hash and would report "no handoff arrived" over a sign-in that is working. A `useRef` makes the handoff read-once.

The first version of that test was **vacuous, and a mutation caught it**: with the guard deleted, the suite stayed green. The reason is that the assertion was about the outcome — the page still routes to `/live`, because `adoptTokens().then(navigate)` overrides the false error state a moment later. Rewritten to assert what the guard actually protects, with a profile read that never settles so the page is pinned in `adopting` and the false error is visible rather than transient. Re-run: deleting the guard now fails exactly that one test.

**Mutation evidence.** Always render the local form (`{localLogin && (` → `{(`): exactly 2 tests fail — `draws no local form when there is no local admin` and `says there is no way in, rather than showing an empty page`. Delete the StrictMode guard: exactly 1 fails. Both reverted, suite green at 42.

**Files beyond the card's `paths:`** — the two test files (the exit criteria are assertions, so they have to live somewhere) and `web/src/test/axiosHarness.ts`, the shared axios adapter harness now used by both page suites. `web/src/test/` is not collected as tests (`vite.config.ts` includes `src/**/*.test.{ts,tsx}` only). Deliberate boundary: the S8-02 suites keep their inline harnesses rather than being refactored onto the shared one in this commit — rewriting passing, reviewed tests in an unrelated card makes the diff a reviewer cannot read. Unifying them is a small follow-up.

**Not here, by ownership:** no router and no `App.tsx` — S8-09 owns routes and role-aware nav. Both pages are tested inside a real `MemoryRouter` + `AuthProvider`, so "routes to /live" is proven by arriving at `/live`, not by spying on a `navigate` call.
