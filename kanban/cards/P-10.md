# P-10 — the recorded boxes are pixels; the event view never says which frame

## Deliverable

The plan asks the drawer to draw "the recorded boxes on the snapshot at
`StartedAt`". A box is `[x1, y1, x2, y2]` in **pixels of the detection frame**:
`Detection.as_object()` in `detector/nvr_detector/model.py` sends the corners
untransformed, and `server/api/detector_api.go` stores `s.Objects` verbatim onto
`events.objects_json`. Neither the event view nor the row carries the frame's
size, so the console has to borrow it from the camera row's
`detection_width`/`detection_height` — and those default to **0**
(`server/models/camera.go:60-61`), in which case the worker fell back to
`GO2RTC_MJPEG_WIDTH`/`_HEIGHT`, a server-side value the console is never told.

So on a default installation the drawer cannot place a single box, and S8-06
drew the line there: it shows the count and says it will not guess. That is the
right behaviour for a console, and it is the wrong state for the product — the
boxes are the proof, and the proof is on the server already.

Fix it on the server, in one of these shapes, and say which:

- **carry the frame on the event view** (`det_width`/`det_height`, resolved from
  the camera row with the same fallback the worker uses) — smallest change, and
  the console keeps drawing;
- **normalise the boxes to `0..1` at write time**, so a box is a position rather
  than a pixel and needs no frame at all — the honest shape, but it changes what
  is stored, so it needs a migration for rows already written and a decision
  about what the webhook payload says;
- **normalise on read only** — no migration, but then the row and the payload
  disagree about the same number, which is the kind of split this repo has been
  careful to avoid.

## Exit criteria

- [ ] the choice is written here, with why the other two lost
- [ ] a drawer on a **default** camera row (detection_width/height at 0) draws the
      boxes where they belong, and a test pins one box's position against a known
      frame
- [ ] the rule is stated in `docs/api.md`'s event section: what space `objects[].box`
      is in, and what a receiver is supposed to do with it
- [ ] the webhook payload and the event view agree about that space (they are read
      by the same third parties)

## Verification

`docker run --rm -v $PWD/server:/src -v nvr-gomod:/go/pkg/mod -w /src golang:1.26 go test ./api -count=1 -run Event`

`cd web && npm run test:run` — `EventDetail.test.tsx` already asserts the
pixel→canvas mapping (`100/640` of the canvas) and the refusal when the frame is
unnamed; whichever shape wins, the refusal test becomes a placement test.

## Notes

Found 2026-11-06 while building S8-06's drawer. The zone polygons do not have
this problem — they are validated into `0..1` on write
(`PUT /api/v1/cameras/:id/zones`), which is exactly why the drawer can always
draw a zone and can never draw a box on a default camera. The asymmetry is the
tell: the same picture, two coordinate spaces, one of them anchored to a knob
nobody set.

Not fixed inside S8-06: the fix is a server contract (what `objects[].box` means)
and possibly a migration, and S8-06's deliverable is the console. The console's
half — count stated, position refused — is shipped and tested.
