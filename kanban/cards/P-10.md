# P-10 — the recorded boxes are pixels; the event view never says which frame

## Deliverable

The plan asks the drawer to draw "the recorded boxes on the snapshot at
`StartedAt`". A box is `[x1, y1, x2, y2]` in **pixels of the detection frame**:
`Detection.as_object()` in `detector/nvr_detector/model.py` sends the corners
untransformed, and `server/api/detector_api.go` stores `s.Objects` verbatim onto
`events.objects_json`. Neither the event view nor the row carries the frame's
size, so the console has to borrow it from the camera row's
`detection_width`/`detection_height` — and those default to **0**
(`server/models/camera.go:60-61`), in which case the worker fell back to
`GO2RTC_MJPEG_WIDTH`/`_HEIGHT`, a server-side value the console is never told.

So on a default installation the drawer cannot place a single box, and S8-06
drew the line there: it shows the count and says it will not guess. That is the
right behaviour for a console, and it is the wrong state for the product — the
boxes are the proof, and the proof is on the server already.

## The choice: carry the frame on the event, resolved at intake and persisted

**Option 1 won, with one amendment to the card's sketch**: the frame is not
re-derived from the camera row on read — it is **resolved once at signal
intake and stored on the event row** (`events.det_width`/`det_height`,
migration v3, `0` = "not named"). The resolution is the same rule that renders
the tap: `go2rtc.DetectionFrameSize(camera, cfg)` is the extracted heart of
`detectionSource` (camera row's `detection_width/height`, `GO2RTC_MJPEG_*`
underneath), now exported and called by both the renderer and the intake, so
the stored number is by construction the size go2rtc was asked to transcode
to — and the worker's decoded frames, and therefore its boxes, are that size.
The detail view answers `det_width`/`det_height`; the drawer divides by them
and never reads the camera row for placement.

Why persist rather than resolve on read (the card's literal sketch): a row
read on a Tuesday after an operator edited the camera or the installation
changed `GO2RTC_MJPEG_WIDTH` would name a frame the boxes are *not* pixels
of. The frame is a fact about the moment the boxes were recorded, and facts
about a moment belong on the row that happened in that moment. It also means
the answer survives the camera row's own edits.

**Option 2 (normalise to `0..1` at write time) lost** because the rows already
written are exactly the ones this card exists for: their frame size is the
unknown, so they cannot be retroactively normalised — the migration would
convert the new and leave the old in pixels, which is two spaces in one
column. It is also a breaking wire change for every receiver that already
divides by a frame it was told out-of-band.

**Option 3 (normalise on read only) lost** for the reason the card itself
gave: the row and the payload would disagree about the same number, and this
repo has been careful never to let one fact have two values.

Edge cases, stated rather than papered over:

- **Mid-event tap-size edit**: the frame stored is the one the first signal
  that named a frame recorded; a `detection_width` edit during a live event
  gets one frame wrong, and `docs/api.md` says so. The store fills a frame
  the row does not yet name and never overwrites one it does.
- **No frame anywhere** (row 0, cfg 0): the event survives with `0×0` — the
  event is the fact, the frame is its annotation — and every consumer that
  finds 0 places nothing. The drawer's refusal is now for these rows only.
- **The demo camera**: its tap reads the fixture JPEG at the picture's own
  size, not at the configured numbers (`DemoDetSource`); documented in the
  `DetectionFrameSize` comment as the one exception.
- **The webhook payload carries no boxes at all** (classes, zones, rules, two
  media URLs — `server/webhooks/webhooks.go` `Payload`), so criterion 4 is
  satisfied by the docs saying so: there is no second place the space has to
  agree with.

## Exit criteria

      caveat, and that the webhook payload carries no boxes
- [x] the webhook payload and the event view agree about that space — the
      payload has no boxes; `docs/api.md` says so where a receiver would look

## Notes

Found 2026-11-06 while building S8-06's drawer. The zone polygons do not have
this problem — they are validated into `0..1` on write
(`PUT /api/v1/cameras/:id/zones`), which is exactly why the drawer can always
draw a zone and can never draw a box on a default camera. The asymmetry is the
tell: the same picture, two coordinate spaces, one of them anchored to a knob
nobody set.

Not fixed inside S8-06: the fix is a server contract (what `objects[].box` means)
and possibly a migration, and S8-06's deliverable is the console. The console's
half — count stated, position refused — is shipped and tested.

Deviation from the card's sketch, in the card's own spirit: the sketch said
"resolved from the camera row with the same fallback the worker uses" (read
time); what shipped resolves at intake and persists, because a read-time
resolution re-derives the frame from knobs that can move after the boxes were
recorded. The drawer's `cameraProblem` caption path went with it — the camera
row is now only needed for the zone polygons, and a drawer that cannot read
the row still places every box.
