# S5-07 — motion.py: CPU gate (160px grayscale absdiff, 1%, continuous mode only)

## Deliverable

Downscale to width 160 grayscale, absdiff vs previous, threshold 17, countNonZero/area < 0.010 -> skip inference. Never gates events-mode cameras (a gate would erase the trigger).

## Exit criteria

- [x] identical frames skip inference
- [x] a moved 16x16 block passes the gate
- [x] gate is provably inert in events record mode (asserted at the pipeline seam)

## Verification

`cd detector && python3 -m pytest tests/test_motion.py -q`

**Observed** 2026-11-03, in `nvr-detector:dev`: `11 passed in 0.07s`.

The tests are written at 160×90 — the size the gate compares at — so the arithmetic
in them is the arithmetic the gate does: 1% of 14 400 px is 144 px.

- `test_an_identical_frame_is_skipped` — three copies of one frame, one inference, and
  the first frame inferred because there is nothing to compare it against.
- `test_a_moved_block_is_inferred` — the same 20×20 block somewhere else passes. A gate
  keyed on how much of the frame is bright rather than on how much of it differs would
  pass this test by accident and miss a person walking.
- `test_a_change_smaller_than_one_percent_of_the_thumbnail_is_skipped` — 10×10 px of
  14 400 is 0.69%, under the plan's 1%, and `last_ratio` says so.
- `test_a_level_change_at_the_threshold_does_not_count` — a whole-frame change of
  exactly `MOTION_THRESHOLD` (17) is nothing, and 18 is something: the comparison is
  `> threshold`, and the two cases are run on separate gates so the second is not
  compared against the first.
- `test_the_gate_measures_a_160_px_wide_grayscale_thumbnail` — a 1920×1080 frame
  becomes a 160×90 single-channel array. That is the whole CPU argument (14 400 px
  against 2 073 600), so it is asserted rather than narrated.
- **The events-mode criterion is asserted at the pipeline seam**, not only on the
  gate: `test_the_gate_is_inert_for_an_events_camera` in `test_pipeline.py` builds a
  `CameraPipeline` for a `record_mode=events` camera, asserts `pipeline.gate.enabled
  is False`, feeds three identical frames through `run`, and asserts
  `inference_runs == 3`. The continuous-mode counterpart asserts the same three frames
  give `inference_runs == 1`.

## Notes

- **`MOTION_WIDTH == 160`, `MOTION_THRESHOLD == 17`, `MOTION_RATIO == 0.010`** are
  asserted as constants, so a retune is a decision someone made in a commit and not
  one a rebase made for them.
- **Switching the gate off drops the comparison state.** `set_enabled` clears
  `_previous`, so re-enabling mid-stream does not compare the first new frame against a
  frame from before the switch. `test_switching_the_gate_off_drops_the_comparison_state`
  pins that: the frame after a re-enable is inferred, and the one after that is not.
- **The gate is the only stage allowed to drop a frame**, which is why its numbers are
  tested in both directions. Too eager and an intrusion is invisible; too loose and a
  branch moving in the wind keeps an event open at 5 fps forever — the idle close
  (10 s) never fires while hits keep landing.
- **`passed`/`skipped` counters exist for the log line**, not for the tests: a worker
  that skipped 94% of a camera's frames is doing its job, and an operator debugging "
  why did nothing get detected" wants that number in the log.
