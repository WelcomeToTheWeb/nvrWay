## Notes

**Unblocked 2026-11-06.** Nothing external stands in the way: S8-10 landed
`web/src/stores/realtime.ts`, which holds `recorder.status` keyed by camera id,
and it is the last dependency. The card sat marked Blocked a step longer than it
should have — it named S8-05, then S8-10, and the board kept the label after the
last one closed.

What the second criterion still needed was this card's own work, not another
card's: a status line on the wall that reads `useRealtime`'s `recorders[camera_id]`
instead of polling. `LivePage` (S8-05) answers what the *media* is doing —
connecting, playing, offline in go2rtc's words, unreachable, ended — which is a
different fact from whether the camera is recording and when its last segment
closed. Both belong on the tile; only the first exists.

What is already true, so the next reader does not start from zero:

- **The broadcast exists.** `Recorder.recorderStatus` (server/media/segments.go)
  sends `{camera_id, mode, segment_seconds, last_segment_at}` and is called from
  `tailSegments`'s `drain` once per ingested segment row — one per closed segment,
  never per frame. `last_segment_at` is that row's `end_ts` in RFC3339, the server
  clock the manifest and the clips are measured on. `Broadcaster.RecorderStatus` is
  the hub seam S2-10 ships, and `ws/hub.go` has the message type.
- **The first criterion was testable and untested.** No suite counted the
  broadcasts; `fakeHub.recorderStatuses()` already collected every payload. That
  assertion is what `status_test.go` lands.

### Done 2026-11-06

**The broadcast needed no code, and that is the honest summary of the server
half.** The call site in `drain` was already correct; what was missing was the
count. `status_test.go` adds three: one per segment (three closed segments, three
broadcasts, asserted as a *maximum* after the tail keeps ticking, so a per-tick or
per-frame announcement fails), one keyed by camera (an `off` camera that never
spawns gets no line — the broadcast follows footage, not the row), and one that a
list line which wrote no row announces nothing.

**`segment_seconds` is the configured length, not the measured one.** The payload
carries `r.Cfg.SegmentSeconds`, and the test asserts exactly that. The line says
what the installation cuts footage into; ffmpeg closes on the nearest keyframe, so
a segment that ran 5.4 s on a 5 s setting does not change what the recorder is
*set* to do, and a number that jittered every tick would be unreadable.

**The tile's line stops short of the word `recording`.** It reads `last segment
20:46:12 · continuous · 5s segments`. The feed proves the last segment closed; it
does not prove the next one will, and a camera whose ffmpeg died keeps showing its
last closed segment until `camera.status` says offline — which is the server's own
announcement of that, on the line above it, from S4-04.

**Rejected — a derived `stalled` verdict** (last segment older than ~2×
`segment_seconds`): rejected. It needs a timer re-rendering the tile against the
wall clock, which is the polling the card forbids in a different costume, and it
duplicates `camera.status`, which the server already broadcasts the moment ffmpeg
dies — a faster and better-informed source than an age heuristic.

**Rejected — one stale-feed warning per tile**: rejected. The store already knows
the socket is `stale`/`refused`; a per-tile caveat would be seven banners on a
wall of seven cameras. Feed health is the shell's (S8-09) one banner, as S8-10's
notes decided.

**The wall opens the feed, and nothing on the wall closes it.** `LivePage` calls
`useRealtime.getState().connect()` on mount. It is the first consumer, so it is
the first caller — S8-10 shipped the store with no `connect()` anywhere. It does
not `disconnect()` on unmount: the store is one socket per tab and the pages that
follow (events, storage) read the same slices, so a tile leaving must not drop the
feed the next page needs. `disconnect()` stays the shell's call, made when the
session ends. `connect()` is idempotent, so StrictMode's double-invoke costs
nothing, and with no access token it opens nothing and says why in `reason`.

**Deviation — S8-10's `RealtimeStore` type erased the hook.** It was declared
`StoreApi<…>`, which has no call signature, so `useRealtime((s) =>
s.recorders[id])` — the subscription the module's own comment promises ("the pages
subscribe to slices of it") — did not typecheck. It is now
`UseBoundStore<StoreApi<…>>`, which is what `create` actually returns;
`getState`/`setState`/`subscribe` are unchanged, so `realtime.test.ts` needed no
edit. `tsc` found it; the first page to consume the feed is what exposed it.

**The timestamp is shown in the operator's clock, not UTC.** The wire value is UTC
because the server owns event time; the wall is read by a person who lives in a
timezone. A value this build cannot parse is rendered **verbatim** rather than as
`Invalid Date` — the server's oddity is information, the formatter's complaint is
not.

### The "flaky media segment tests" were never flaky

The harness board's `Investigate the flaky nvr/server/media segment tests (9
timeouts at 5s)` card is closed by this work, with a different diagnosis than its
own framing. `helpers_test.go`'s `segmentsFor` read the manifest with
`ListRange(cameraID, time.Now().Add(-48h), time.Now().Add(48h), 0)` — the **host's**
clock — while every row it reads is stamped by the recorder's injected `fakeClock`,
fixed at **2026-11-03T12:00Z**. Real time does not stop: on 2026-11-04 the fake
rows sat just inside the 48 h window (and tests that advance the fake clock landed
on either side of its edge, which is what read as "the failing set differs between
runs"); by 2026-11-06 they were all outside it, and the nine failed every time.
Deterministic, monotonically worsening, and nothing to do with timing.

The fix is the helper's window: `time.Unix(0,0)` to `2200-01-01`, with the reason
in the comment. A helper whose answer depends on the date the suite runs is not a
helper. Production callers (the timeline manifest, the clip window) keep their real
windows and their own suites.

Evidence: `go test ./media -count=1` in `golang:1.26-ffmpeg` — green three
consecutive runs (13.4 s, 12.1 s, 12.1 s), and `go test ./... -count=1` green in
every package. The card's acceptance asked for green on three consecutive runs;
that is met, by branch (a)'s spirit with a correction: the fixtures did not need
to wait on an event, they needed a helper that stops asking the host what day it
is.
