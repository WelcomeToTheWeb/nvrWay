# S4-06 — recorder.status broadcast (one per segment tick)

## Deliverable

Broadcast {camera_id, mode, segment_seconds, last_segment_at} per completed segment — not per frame.

## Exit criteria

- [ ] one broadcast per segment
- [ ] the LivePage status line reads from it (no polling)

## Verification

`docker run --rm -v $PWD/server:/src -w /src golang:1.26 go test ./media -count=1 -run Status`

## Notes

BLOCKED on Step 8: the card's second criterion is "the LivePage status line reads
from it (no polling)", and there is no LivePage until S8-05 (web console, backlog).
The deliverable is a status *line*, and the line is the console's, so the card
cannot be closed against a screen that does not exist yet. The broadcast itself is
not blocked, and neither is a suite for it — see below.

What is already true, so the next reader does not start from zero:

- **The broadcast exists.** `Recorder.recorderStatus` (server/media/segments.go)
  sends `{camera_id, mode, segment_seconds, last_segment_at}` and is called from
  `tailSegments`'s `drain` once per ingested segment row — one per closed segment,
  never per frame. `last_segment_at` is that row's `end_ts` in RFC3339, the server
  clock the manifest and the clips are measured on. `Broadcaster.RecorderStatus` is
  the hub seam S2-10 ships, and `ws/hub.go` has the message type.
- **The first criterion is testable today and is not yet tested.** No suite counts
  the broadcasts. `fakeHub.recorderStatuses()` already collects every payload in
  order, so "one per segment" is a few lines against the fake source — or against
  S4-07's lavfi recorder, where the segment count is known from ffmpeg's own list.
  Whoever unblocks this card should land that assertion with it; the recorder's
  per-segment call site has no test holding it in place.
- **The card's verification command names `-run Status`,** a test name that does
  not exist yet — the suite above is where it belongs.
