# S5-08 — client.py: ServerClient config poll + signal POST with backoff

## Deliverable

GET /api/internal/v1/detector/config every 5 s; POST /api/internal/v1/signals; 3 retries + min(5*2^n, 60) s backoff; buffer flushed every 2 s, max 40 per POST, drop-oldest with a counted signals_dropped log.

## Exit criteria

- [x] serialization shape matches the plan's signal JSON keys exactly
- [x] 500, 500, 200 -> 3 attempts asserted against a local http.server stub
- [x] buffer survives a dead server and flushes on recovery
- [x] 40-signal cap drops oldest with a counted log line

## Verification

`cd detector && python3 -m pytest tests/test_signals.py -q`

**Observed** 2026-11-03, in `nvr-detector:dev`: `21 passed in 2.65s`.

- **Serialization.** `test_signals_are_posted_as_the_plan_shapes_them` asserts the body
  is `{"signals": [signal]}`, the URL is `/api/internal/v1/signals`, and
  `tuple(signal.keys())` equals `PLAN_SIGNAL_KEYS` — the twelve keys transcribed from
  the plan's line 181 into the test, not imported from the module, so a rename fails
  instead of following itself. The token rides as `Authorization: Bearer <token>` and
  the timeout is the worker's.
- **The retry criterion, over a socket.** `StubServer` is a real
  `ThreadingHTTPServer` on 127.0.0.1 whose handler scripts 500, 500, 200 and counts
  what it was asked. The test asserts `server.count(SIGNALS_PATH) == 3` — three
  attempts, not three more — and that the waits were `[5.0, 10.0]`. The client's own
  log for that exchange:

  ```
  client: signals: HTTP 500 (db locked), attempt 1 of 4, retrying in 5s
  client: signals: HTTP 500 (db locked), attempt 2 of 4, retrying in 10s
  ```

  A server that never answers is asked four times (`MAX_RETRIES + 1`) with
  `[5.0, 10.0, 20.0]`, and `_backoff_delay` is asserted as
  `[5.0, 10.0, 20.0, 40.0, 60.0, 60.0]` — `min(5 * 2^n, 60)`.
- **The buffer survives a dead server.** Four refused connections in a row leave both
  signals buffered and `flush()` false; the next flush posts them and the test asserts
  the posted order is `open, extend` — the order the events happened in — and that
  `signals_sent == 2`.
- **The cap.** Forty-five signals through a 40-signal buffer: `buffered() == 40`,
  `signals_dropped == 5`, the surviving window starts at signal 5, and every drop is
  logged with the running count (one line per dropped signal):

  ```
  client: signals_dropped=5: the signal buffer holds at most 40, dropping the oldest 1
  ```

## Notes

- **A 4xx is not retried.** 403 means the token is wrong — `client: signals refused
  with HTTP 403: internal api disabled` — and a worker that retried it four times
  would only delay the line that says so while hammering a server that has already
  answered. 429 is the exception: it means "not now", so it goes down the retry path.
- **A 200 that means no is surfaced, not swallowed.** The server answers
  `{"accepted":0,"events":[{"error":"unknown camera"}]}` with a 200 (S5-10), so
  `post_signals` returns `(ok, body)` and the caller can name the camera the server
  could not find. `flush()` stays a plain bool because the loop only needs "did the
  buffer drain".
- **A flush removes the signals it posted by identity, not by count.** The buffer is
  shared with the camera threads, so signals can be added — and dropped by the cap —
  while a POST is in flight. `test_signals_added_while_a_post_is_in_flight_are_not_
  double_counted` runs with `max_batch=1` and asserts each signal is posted exactly
  once and none is lost behind it.
- **The stub session is strict by default and forgiving on request.** It raises when a
  test's script runs out, because an unexpected call is a finding; the pipeline tests
  hand it a `default` because they are testing reconciliation, not the transport.
- **The loop is tested at compressed intervals** (`poll=0.15`, `flush_every=0.05`) so
  the shape — poll, flush, poll, drain — is asserted in under a second instead of
  thirty.
