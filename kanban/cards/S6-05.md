## Notes

Seek-on-remote is a v2 item (README Roadmap).

**What shipped.** `EventClip` and `EventSnapshot` now resolve "where are the bytes"
in one order — local file, then the tier, then a named 404 — through
`serveLocalClip` / `serveLocalSnapshot` (both return false when they wrote nothing,
so the tier gets its turn without unwinding a half-written response) and
`streamFromTier` for the remote path. The local path is `http.ServeContent`, which
is what answers `Range` with 206 and `If-Modified-Since` with 304.

**The remote path calls `Stat` before `Get`.** One extra round trip per play,
bought for a `Content-Length` that is true and a 404 that arrives *before* a 200's
headers have gone. Without the first, a player cannot show progress or duration;
without the second, a drawer shows a clip that stops halfway instead of saying
there is no clip.

**A remote `Range` request gets the whole object with a 200.** `Backend.Get` has no
offset and no length, so there is nothing to answer a range with. Every tier behind
the interface *can* read a range — minio's `GetObject` takes `Offset`/`Length`,
WebDAV answers `Range`, `pkg/sftp` has a `ReaderAt` — so the gap is one method on
one interface, not a limit of the tiers. `docs/architecture.md` § Playback and the
remote seek gap states the gap, what the console should do with a remote clip, and
what v2 adds. Clip assembly already passes `-movflags +faststart`, so the `moov`
atom is at the front and a remote clip *starts* promptly today; only the seek is
missing.

**The fs driver now tells a missing object from a missing mount.** `os.Stat`
answers `ENOENT` for both, so an unmounted media volume looked, for every clip at
once, exactly like a house with no recordings — a 404 that read as "never
recorded". `fs.Stat` and `fs.Get` check the root once, on the miss path only, and
report `bucket missing`. `fs.Ping` and `fs.List` already refused a root that is not
there (S7-03, S7-10); a read that reported the same situation as "no such object"
was the one path hiding it. `TestFSReadRefusesARootThatIsNotThere` pins both sides.

**The route answers are separated on purpose.** `404 clip not available` covers no
copy anywhere, an object gone from a tier that *is* there, and no backend
configured at all — facts about retention and about the installation. `502
{"error":…,"tier":"<name>"}` covers a tier that is configured and not usable, and
carries the named state (`bucket missing`, `bad credentials`,
`discovery_unreachable`, `sftp host key changed`) because those are different
fixes. `ErrBadKey` answers 500 with `tier: ""` — it is not one of the four
connection names, and it is an environment problem rather than a tier state.

**Two deviations from the card's `paths`, both deliberate.** The tests live in
`server/api/clip_test.go` rather than `events_test.go`, which already holds the
list/detail/delete surface and the `eventsFixture` these tests reuse. And the
snapshot route got the same tier branch as the clip route: an event whose footage
aged out locally still has its picture on the tier, and a drawer that plays a clip
around a broken `<img>` is a bug the console cannot fix from the event view alone.
The two media routes resolve "where are the bytes" the same way or they disagree
inside one drawer.
