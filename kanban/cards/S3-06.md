## Notes

**Observed** 2026-11-02: the command above, `ok  nvr/server/api 1.551s`.

The matrix is asserted as a table (endpoint × role → status), not one test per
route: the failure this guards is a single missing gate on a single route, and a
per-route test a later card forgets to add is exactly how that happens. Adding a
route means adding a row.

- Camera floor: viewer reads list/detail/snapshot; operator adds create, update,
  probe and zone writes; delete is admin-only. Every one of the 8 routes answers
  401 with no token, before any role question.
- The refusals are ledger rows under the verb the route declared in Step 2's denial
  registry, with the actor named. A refused create names the **route** (there is no
  camera id yet); a refusal about one camera names that camera. The suite asserts
  both shapes.
- **`GET/POST/PUT/DELETE /api/settings/oidc` did not exist**, so this card mounted
  it (`api/oidc_settings.go`) on the existing admin group, declared its ledger
  verbs in the denial registry, and added `AuditOIDCRead` (`oidc.read`) to the
  verbs. Discovery runs at save time, as `sso/discovery.go` requires: a provider
  whose issuer does not answer is a 422 carrying the named state
  (`discovery_unreachable`) and no row lands. The client secret is write-only
  (`secret_set: true`, never echoed), and the redirect URI has one author — the
  server computes it and answers it on every read.
- New routes' denials are asserted audited too, not just the camera ones.

Storage-backend and webhook admin floors arrive with their own routes (S7-10,
S6-07); the events/clips read floor arrives with S6-04. The rows for those are
added to this table when the routes exist.
