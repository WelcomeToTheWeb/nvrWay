# Agent Note: zone-editor-canvas-and-two-write-paths

Status: implemented

## Problem

The console has to let an operator draw the polygon rules a camera detects inside (S8-07), and three things about that were unsettled in a way code alone cannot answer later. (1) Where the geometry lives: the plan says `<canvas>`, and a canvas is a bitmap whose size is whatever CSS gave it, so a rule stored in canvas coordinates changes when the window does — and a headless suite has no pixels to read back. (2) Who decides a polygon is legal: `server/api/zones.go` declares "One validator, three readers (console, API, worker)", and the card's exit criterion demands that a 2-vertex attempt be refused *with the server's 422 message* — which cannot happen if the console refuses first. (3) Which route a camera save writes: `cameraInput` accepts `zones` as well as the row's fields, so the obvious "spread the row into the body" form writes the rule set through the route that has no zone audit row and no polygon normalisation.

## Decision

`web/src/components/ZoneEditor.tsx` keeps every vertex in React state as a `0..1` pair and repaints the `<canvas>` from that state; the canvas is never a source of truth. A pointer is converted on arrival by `toNormalized` in `web/src/api/cameras.ts` (clamped to `0..1`), and every pixel drawn afterwards is derived from the stored number, so a resize cannot drift a rule. Painting bails before asking for a 2d context when the element's box is zero-sized, which is what lets the suite stub `getContext` to `null` (a platform without one) and drive clicks and keys instead. The rule badge is a DOM button positioned at the zone's first vertex as `left: x*100%` / `top: y*100%`, not canvas text — readable at any density, keyboard-reachable, and the stored number read back the other way.

The console advises and never refuses: Enter closes whatever is on the board including a two-vertex shape, the editor states its own warning ("the server wants 3–32"), and the refusal is the server's 422 rendered in both halves — `error` (`zone polygon invalid`, the fixed contract string) and `detail` (which zone, and what about it). `serverDetail` in `web/src/api/client.ts` is the sibling of `serverWords` for that second half. `enclosesArea` in `api/cameras.ts` is used to warn, never to block.

Two write paths stay apart: the row form builds its body from a named field list (`RowWrite`) that has no `zones` key and PUTs `/api/v1/cameras/:id`; the polygons PUT `/api/v1/cameras/:id/zones` and the editor adopts the server's returned array as its new confirmed baseline. "Saved" is computed against that internal baseline, not against the `camera` prop, because `CamerasPage` passes a fresh object literal every render. Zone ids come from `mintZoneId` (monotone `Date.now().toString(36)` + counter) because the server checks duplicate ids only within the array it was sent, and event rows store zone ids resolved to names on read. The slug is displayed and not editable. `CamerasPage` reads `useMatch('/cameras/:id')` and renders the editor from the list it already fetched (the list route answers the full `cameraView`), so a deep link is one request; S8-09 must mount it at both routes.
## Alternatives considered

Refusing an illegal polygon in the editor before sending it — lost because it makes the card's own exit criterion unrunnable (no request, so no 422 to read) and installs a fourth validator that can disagree with the server's; the console's opinion is shown as a warning line instead. Deriving "unsaved" from the `camera` prop (reset the board when the row changes) — lost because `CamerasPage` passes `camera={{ ...camera, zones }}`, a new object literal on every render of the row form, so an effect keyed on it would discard a half-drawn polygon on every keystroke in the name box; the editor owns its confirmed baseline and a camera switch resets it by remount (`key={camera.id}`). Editing the slug in the row form — lost because the slug is the name of every stored key the camera has written (`nvr/<slug>/<YYYY>/<MM>/<DD>/…`), so renaming is a footage migration the console does not perform; the field is shown, not offered. Drawing the rule badge as canvas text — lost on accessibility and testability: it cannot be read at arbitrary density, cannot be focused, and cannot be asserted against. Pointer events with `setPointerCapture` unconditionally — lost to jsdom (no capture API); capture is feature-detected and a drag that ends at the canvas edge is accepted as a drag.
## Consequences

27 new tests (`ZoneEditor.test.tsx` 14, `CamerasPage.test.tsx` 13); the console suite is 157 across 11 files and `tsc --noEmit` is clean. Eight mutations were run and each failed exactly the test that claims the behaviour, including the two contracts most likely to be "simplified" later: the bare-array PUT body, and the row form not carrying `zones`. Follow-ups recorded on the board: S8-09 now carries the obligation to mount `CamerasPage` at both `/cameras` and `/cameras/:id` (a route table that points `:id` elsewhere loses the zone editor silently), and S8-13 owns the admin-only delete with a confirmation that names the counts it will destroy. Known gaps left on purpose: the editor's aspect ratio is a placeholder until the snapshot loads (`detection_width/height` describe the detection input and default to 0, so they are not the stream's shape — the image's own aspect takes over on load); a snapshot 404 does not block drawing, it only states itself; the delete button, the router/nav, and i18n are not here.
