# Agent Note: recorder-status-segment-tick-line

Status: implemented

## Problem

The recorder has announced `recorder.status` since S4-03, and S8-10's store has held it keyed by camera id since S8-10, but nothing counted the announcements and nothing rendered them. So the wall answered "what is the media doing" (S8-05's LivePage) and was silent on the different question an operator asks about an NVR: is this camera actually producing footage, and when did the last piece of it land. An uncounted broadcast is also an unguarded one — "one per segment, not per frame" was a sentence in the plan with no test holding it, and the recorder's tail drains on a ticker, which is exactly the shape that turns into a per-tick or per-frame feed by accident.

## Decision

`server/media/status_test.go` counts the existing broadcast at its existing call site (`tailSegments`'s `drain`, one `Recorder.recorderStatus` per ingested segment row). Three suites: three closed segments produce exactly three broadcasts — asserted as a maximum after the tail keeps ticking, so a per-tick or per-frame announcement fails; a camera in `record_mode=off` that never spawns produces none, so the payload's `camera_id` is proven to follow footage rather than the row; and a segment-list line that does not parse announces nothing, because the broadcast happens after the manifest insert, not at the CSV read. The payload's `segment_seconds` is `r.Cfg.SegmentSeconds` — the configured cut length, not the measured segment duration — and `last_segment_at` is the row's `end_ts` in RFC3339, the server clock the manifest and clips are measured on; no broadcast carries a `time.Now()`.

`web/src/pages/LivePage.tsx` renders a `RecorderLine` per tile, below the media-state line and unconditionally — it is not gated on `playing`, because a camera can be recording and unwatchable, or watchable and dead. Its text is `last segment <time> · <mode> · <N>s segments`, or `no segment yet — the recorder has not closed one for this camera` when the feed has never reported one. It reads `useRealtime((s) => s.recorders[camera.id])` and issues no request: the wall still makes exactly `/v1/settings/live` and `/v1/cameras`, which is what the no-polling test asserts. `segmentClock` formats the UTC wire value in the browser's locale and timezone, and renders an unparseable value **verbatim** rather than as `Invalid Date`.

The wall owns the feed's opening and nobody owns its closing: `LivePage` calls `useRealtime.getState().connect()` on mount and never calls `disconnect()`. `connect()` is idempotent (`if (socket) return`), so StrictMode's double-invoke costs nothing, and with no access token it opens nothing and records the reason in the store. `disconnect()` is reserved for the shell (S8-09) to call when the session ends.

`RealtimeStore` in `web/src/stores/realtime.ts` is `UseBoundStore<StoreApi<RealtimeState & RealtimeActions>>`, not a bare `StoreApi`. The bare form has no call signature, so the subscription the module's own comment promises — "the pages subscribe to slices of it" — did not typecheck; `getState`/`setState`/`subscribe` are unaffected, so `realtime.test.ts` is unchanged.

`server/media/helpers_test.go`'s `segmentsFor` reads the manifest over `time.Unix(0,0)` .. `2200-01-01`. A test helper reading rows written by an injected clock must not anchor its window on the host clock — see the flake diagnosis in `kanban/cards/S4-06.md`.
## Alternatives considered

A derived `stalled` verdict (last segment older than ~2× `segment_seconds`) was rejected: it needs a timer re-rendering the tile against the wall clock, which is the polling the card forbids wearing a different hat, and it duplicates `camera.status`, which the server broadcasts the moment ffmpeg dies (S4-04) — a faster and better-informed source than an age heuristic. The word `recording` was rejected from the line for the same reason: the feed proves the last segment closed, not that the next one will, and a camera whose ffmpeg died keeps showing its last closed segment until `camera.status` says otherwise. One stale-feed caveat per tile was rejected — the store already knows the socket is `stale`/`refused`, and a wall of seven cameras would grow seven banners; feed health stays the shell's single banner, as S8-10's note decided. `useStore(useRealtime, selector)` in the page was rejected as a workaround for a type that lies about its own documented interface, in favour of fixing the type. And in the Go suite, widening only the new test's own segment query was rejected in favour of fixing the shared helper, which was silently failing nine other suites.
## Consequences

Bought: the plan's "one per segment, not per frame" is now a counted property with mutation evidence (per-tick, doubled, and wrong-`mode` mutations each fail the test that claims them); the wall states recording and watchability as two facts on one tile; the first consumer of the realtime store exists, so its type and its `connect()` contract are now exercised rather than theoretical; and `go test ./...` is green in every package for the first time since the helper expired, which restores the repo's own gate as evidence.

Costs and obligations: `LivePage` is currently the only caller of `connect()`, so a console that mounts no LivePage has no feed — when S8-09's shell lands it should take ownership of the socket's lifecycle (and decide whether `disconnect()` belongs on logout, on unmount, or nowhere). The recorder line has no freshness signal of its own: a dropped socket leaves the last closed segment on screen looking current until the shell's banner says otherwise, which is a deliberate deferral to S8-09, not an oversight. `segment_seconds` being configured rather than measured means the line cannot show ffmpeg keyframe drift — accepted, since the clip builder already measures the real durations. The `-run Status` filter in the card's verification command also matches `TestCrashCameraStatusNamesTheTruth`; left as the card wrote it.
