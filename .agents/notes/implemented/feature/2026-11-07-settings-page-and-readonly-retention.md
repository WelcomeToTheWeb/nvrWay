# Agent Note: settings-page-and-readonly-retention

Status: implemented

## Problem

The console needed a Settings surface for the storage tier (S7-10), webhooks (S6-07) and OIDC providers (S2-07), and the card's title named "retention" as a fourth section. But retention is authored entirely by the environment (LOCAL_RETENTION_DAYS / REMOTE_RETENTION_DAYS / EVENT_RETENTION_DAYS) and honoured by the sweeper — there was no route that told the console what the installation actually runs, so a retention tab had nothing honest to show. The card's exit criteria also demanded that the four named connection-test states, the set/unset secret rendering, and the storage.queue counts reach the operator as the server's own words.

## Decision

`GET /api/settings/retention` (admin, `server/api/retention.go`) answers the retention policy read from the loaded config: `local_days`, `remote_days` with `remote_forever` spelled out beside a zero, `event_days`, `unuploaded_protection_days`, the three housekeeping windows (from `sweeper.Default*RetentionDays`), and `author: "environment"`. It is read-only by contract — there is no write path, and the page says so. The protection-window formula has a single author: `sweeper.UnuploadedProtectionDays(localDays)` (`max(3 × localDays, 7)`), which the sweep's `protectionWindow` now derives from and the API reports. `web/src/api/settings.ts` mirrors the server views verbatim (no renames) and owns `storageWrite`, the diff helper that enforces the secret rule: every secret field of the kind is declared to it, and only non-empty ones travel — omitted keeps the stored value, an explicit empty string (sent by a per-field "clear" button) clears it. `web/src/pages/SettingsPage.tsx` draws four URL-addressable tabs (`/settings?tab=…`); the connection test renders the tier's named state verbatim (`ok` / `discovery_unreachable` / `bad credentials` / `sftp host key changed` / `bucket missing`, with `connection_failed` as the honest absence of a name); queue counts read from `GET /storage/queue` and then follow the sweeper's `storage.queue` WS report (`Report.Queue` wins over the mount-time read until a reload); a non-admin gets a refusal rendered before any request fires. `enabled`/`is_default` have their own routes and never ride in the row-write body.
## Alternatives considered

Editable retention (settings rows + sweeper reading them each sweep) — rejected: it forks the policy into an env file and a settings row while the sweep keeps reading the env, which is two authors for one promise, and no exit criterion asked for a write path. Restating the protection formula in the API handler — rejected: the screen and the sweep must never disagree about whether un-uploaded footage is still on disk. Sending the whole row on save (a spread of the view) — rejected: the view carries no secrets, so a spread would either omit changed fields or, worse, a future field added to the view would silently start round-tripping; the diff also keeps `kind`/`enabled`/`is_default` out of a body whose audit row is about the row. Treating `username` as a sealed secret — rejected: `storageBackendView` carries it verbatim; only password/access_key/secret_key/private_key_path are sealed, and the form's SECRET_FIELDS list follows the server's sealing, not the field's appearance.
## Consequences

Cost: v1 has no console-side retention tuning — changing a window means editing the env and restarting, and the tab must keep naming the env vars so the operator is not left hunting. The WS-over-REST precedence for queue counts is deliberately simple (last writer wins, reload resets) rather than timestamp-compared, because the sweeper's report carries no per-message timestamp. Bought: one author for the retention policy and one for its protection formula; the verify.sh gate (S10-03) and the Playwright storage spec (S8-12) can assert the same strings the page renders; the secret rule is pinned by a mutation-tested suite (an empty secret in a save body fails a test).
