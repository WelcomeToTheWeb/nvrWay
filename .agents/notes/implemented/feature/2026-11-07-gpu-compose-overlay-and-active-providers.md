# Agent Note: gpu-compose-overlay-and-active-providers

Status: implemented

## Problem

The GPU overlay card (S9-06) was blocked on a host-state sentence that went stale the day S3-08 landed the NVIDIA container toolkit: the repo claimed CUDA was "documented, not shipped", docs said so, and no one re-probed. Shipping the overlay naively hits three silent traps (PyPI placeholder wheels, CPU-degraded sessions that log success, and a Dockerfile default-target flip that turns the CPU baseline into a 2 GB CUDA image), each of which makes a broken GPU deployment look healthy.

## Decision

`docker-compose.gpu.yml` (repo root) overlays only the detector: device reservation (`driver: nvidia, count: all, capabilities: [gpu]`), `NVIDIA_VISIBLE_DEVICES=all`, `NVIDIA_DRIVER_CAPABILITIES=compute,utility`, `DET_PROVIDERS=CUDAExecutionProvider,CPUExecutionProvider`, and a complete `build:` section (`context: .`, `dockerfile: docker/Dockerfile.detector`, `target: runtime-gpu`) so both the dev and prod compose files build the GPU image; the CUDA variant is deliberately not published to ghcr. `docker/Dockerfile.detector` gains stage 3 `runtime-gpu`: `USER root` for pip, `onnxruntime` replaced by `onnxruntime-gpu==1.31.1` plus `nvidia-cudnn-cu13 nvidia-cuda-runtime nvidia-cufft nvidia-curand nvidia-cusolver nvidia-cusparse` (unsuffixed names — CUDA 13 consolidated the wheels; the `-cu13` suffixed names are 0.0.1 PyPI placeholders), an `/etc/ld.so.conf.d/nvr-nvidia.conf` generated from the site-packages `nvidia/*/lib` globs plus `ldconfig` (no LD_LIBRARY_PATH), then `USER nvr:nvr` back. `ldd libonnxruntime_providers_cuda.so` is the dependency checklist; its only remaining `not found` is `libcuda.so.1`, the driver library the container toolkit injects at runtime, which must never be pip-installed. Because `runtime-gpu` is the final stage, every consumer names its target explicitly: `docker/docker-compose.yml` pins `target: runtime` (a default build would silently tag the CUDA image as `nvr/detector:latest` — this happened in development and the suite caught it). `YoloOnnx._open` in `detector/nvr_detector/model.py` reconciles `self.providers` against `session.get_providers()` after opening: the worker's startup line reports ACTIVE providers, and a silent substitution (CUDA in the build, no GPU reachable) emits a worker-level WARN; pinned by `detector/tests/test_providers.py`. Fallback posture is unchanged: CPU stays in the provider list, a worker without a reachable GPU degrades and warns, it never dies.
## Alternatives considered

A separate `Dockerfile.detector.gpu` lost to stage 3: the GPU image is the runtime stage plus a pip swap, and a second Dockerfile duplicates the model-export provenance for zero gain. `LD_LIBRARY_PATH` env lost to `ld.so.conf.d`: env is per-entrypoint and invisible to `docker exec` diagnostics, ldconfig is system-wide and survives both. Publishing `nvr/detector:gpu` to ghcr lost to build-locally: ~2 GB of CUDA wheels for a path most installs never take, and the CPU image must stay the default pull. Pip-installing `libcuda` was rejected outright — it is the driver ABI the host owns; the toolkit injects it. Keeping the requested-providers log line (documenting the caveat instead) lost after observing the failure directly: the log claimed CUDA while `nvidia-smi` showed no process — exactly the "looks healthy forever" state the repo's docs discipline forbids.
## Consequences

The dev box now runs the GPU worker (`up -d` with the overlay); fresh installs still get CPU by default, so the CPU sizing claim (4–8 cameras) remains the documented baseline and the GPU path carries only a works-verified claim, not a performance one. The base compose must keep `target: runtime` forever — any future stage appended to the Dockerfile inherits the same trap, which the compose comment states. Detector coverage gains three tests; the reconciliation adds one ORT call per boot (negligible). `scripts/gpu-probe.sh --cuda` becomes the standing pre-flight for any GPU claim, and the card's lesson — re-probe before trusting a hardware-blocked status — is recorded there.
