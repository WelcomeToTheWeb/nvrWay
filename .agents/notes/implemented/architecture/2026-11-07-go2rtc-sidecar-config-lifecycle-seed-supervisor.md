# Agent Note: go2rtc-sidecar-config-lifecycle-seed-supervisor

Status: implemented

## Problem

The server renders go2rtc.yaml from camera rows and pushes it with POST /api/config at boot and on every camera write (S3-05), and the boot log promises the config "is re-applied on the next camera save". Against real go2rtc (master, revision 990f4de, verified 2026-11-07) that promise was false in two ways: the WS upgrader installs its CheckOrigin once at process start from the on-disk config (so a fresh-volume sidecar 403s the console, whose origin differs by port — P-15), and the config POST/PATCH handler only validates YAML and os.WriteFile's the file — streams, listens, and credentials are read once at boot and never reloaded, so pushed streams never register in the running sidecar (P-16). The e2e harness had always hidden this by `docker restart`ing the sidecar after seeding; the dev compose had no such step, so on a running stack a new camera's live tile stayed dead ("webrtc/offer: stream not found") until the sidecar happened to restart.

## Decision

The sidecar's config lifecycle is owned by a supervisor in the container command, in both places the sidecar boots (docker/docker-compose.yml go2rtc service, scripts/e2e-stack.sh docker run). The command: (1) seeds /config/go2rtc.yaml from the read-only bind mount /go2rtc.seed.yaml (docker/go2rtc.yaml.template) only when the config file is missing or empty, so api.origin:"*" is on disk at process start on every fresh volume; (2) runs go2rtc in the background; (3) polls md5sum of the config file every 2s and, when it changes — the server just re-rendered it — kills go2rtc and exits 0, so the restart policy (unless-stopped; the e2e container gained --restart unless-stopped and lost --rm, which docker rejects in combination) boots the sidecar with the new file. The server's ApplyConfig whole-file POST stays exactly as S3-01 shipped it: it is now honestly "write the sidecar's next-boot config", and the supervisor is what makes it live. Compose comments state that go2rtc never reloads a config in place and name the cost. The e2e script's explicit `docker restart` after seeding stays as the deterministic instant of the streams' first boot.
## Alternatives considered

Diff-apply via the existing per-stream runtime client (client.go already has PUT /api/streams?src= and DELETE from S3-01, which go2rtc does apply live): rejected because listens, api.origin, and credentials still cannot be applied live, so the restart path stays load-bearing regardless, and a correct diff (deletions, source-list equality) is a feature-sized change, not a fix — recorded in P-16's card as the better long-term answer if the restart blink becomes unacceptable. Documenting "restart the sidecar after camera changes": rejected because it keeps the bug and makes the boot log line a lie on the stack that prints it. Bind-mounting the template read-only at /config/go2rtc.yaml: rejected because go2rtc saves the applied config back to its config path, so every push would end in a write error. Server shells out to docker restart: rejected — needs docker socket access in the server container.
## Consequences

Every camera save restarts the sidecar: live tiles drop (the tile makes one attempt per mount and does not retry — S8-05 design — so a tile caught mid-restart reads "unreachable" until reload), and recorder ffmpeg pulls die and respawn on their existing backoff. go2rtc rewrites its config once at boot (normalization), so each external change costs one extra supervisor restart before converging. The e2e suite now genuinely tests the fresh-volume path (stop wipes the config volume; two consecutive cold runs 15/15), which exposed and paid off a latent cameras.spec.ts scoping bug (filter({has: heading}) matched the ancestor section; fixed to the heading's nearest ancestor section). The behavior is pinned against go2rtc master's current semantics; a future go2rtc that hot-reloads would make the supervisor redundant but not wrong.
